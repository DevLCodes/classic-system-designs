What an ID has to do

On one database, AUTO_INCREMENT solves this for free. Once writes land on many servers or many shards, each one needs IDs that nobody else will ever hand out.

Before you pick a scheme, decide which of these you actually need. They pull against each other.

PropertyWhat it meansWhy you might need it
UniqueNo two records ever share an IDAlways. A duplicate primary key loses or overwrites data.
No coordination per IDA server can make an ID without asking anyoneThroughput and availability: a central counter is a hop on every write and a single point of failure
Roughly time-sortedLater IDs are bigger, give or take a few millisecondsSort by ID instead of a timestamp column; cheap cursors; fast inserts into B-trees
CompactFits in 64 bitsHalf the size of a UUID in every index, foreign key and cache entry
UnguessableSeeing one ID tells you nothing about the nextPublic URLs and invite links, where enumeration is a leak

Time-sorted and unguessable can't both be fully true: if IDs grow with time, an attacker can narrow down the next one. For public links, keep a sortable internal ID and give out a separate random token.

Counters and ticket servers

The simplest answer is still a counter. The question is how to stop it becoming a bottleneck.

Auto-increment

Fine for a single database. It breaks down when you shard: two shards both start at 1. You can give each shard its own offset and step (shard 3 of 8 hands out 3, 11, 19 …), but then adding a ninth shard means changing every step.

Ticket servers

Flickr's well-known fix: a tiny MySQL database whose only job is a counter. An app server runs REPLACE INTO Tickets64 (stub) VALUES ('a') and reads LAST_INSERT_ID(). Two ticket servers, one set to odd numbers and one to even (auto_increment_increment = 2 with offsets 1 and 2), remove the single point of failure. You still pay a network hop per ID, and the two servers drift apart, so IDs are only loosely ordered.

ID ranges (block leasing)

Each app server asks a coordinator for a block, say 1,000 IDs, and hands them out from memory. The coordinator can be one database row updated in a transaction, or a key in ZooKeeper or etcd. At 1,000 IDs a block, a server writing 5,000 rows a second calls the coordinator only five times a second. If a server crashes, its unused IDs are skipped. That's fine: IDs need to be unique, not gap-free.

Never promise gap-free IDs. Rolled-back transactions, crashed servers and abandoned blocks all leave holes. If the business truly needs consecutive numbers (invoice numbers in some countries), make that a separate, slow, carefully serialised counter.

UUIDv4 and UUIDv7

A UUID is 128 bits that any machine can make on its own. No coordinator, no machine IDs. The cost is size: 16 bytes, or 36 characters as text.

UUIDv4UUIDv7
Layout122 random bits, plus 6 bits of version and variant48-bit Unix time in milliseconds, then 74 random bits, plus version and variant
Sorted by time?No, completely randomYes, to the millisecond
Chance of a clashAbout 50% only after 2.7 × 1018 IDs: a billion a second for 86 yearsOnly IDs made in the same millisecond can clash, and 74 random bits makes that vanishingly rare
LeaksNothingWhen the record was created
Index behaviourInserts land all over the B-treeInserts land at the right-hand edge
StandardBoth defined in RFC 9562 (2024), which replaced RFC 4122

UUIDv7's 48-bit millisecond clock lasts until about the year 10889, so running out is not a concern. ULID is an older, similar idea (48-bit time plus 80 random bits, written as 26 characters); if you are starting fresh and your database or library supports v7, prefer the standard.

Snowflake IDs

Twitter's Snowflake (2010) packs a timestamp, a machine number and a counter into one 64-bit integer. Every server makes IDs on its own, they fit in a BIGINT, and they sort by time.

How a generator makes one ID

  1. Read the clock in milliseconds and subtract the epoch.
  2. If it is the same millisecond as the last ID, add one to the sequence. If the sequence passes 4,095, wait for the next millisecond.
  3. If it is a new millisecond, reset the sequence to 0.
  4. If the clock is behind the last millisecond used, refuse or wait (see clocks).
  5. Shift and OR the three parts together.

No network call, no lock shared with other servers. A single generator tops out at 4,096 IDs per millisecond, which is about 4.1 million a second.

Worked example. Take the ID 1541815603606036480. Shift right by 22 bits to get 367,597,485,448 ms; add the Twitter epoch (1,288,834,974,657) and you get 1,656,432,460,105 ms, which is 28 June 2022 at 16:07:40.105 UTC. The next 10 bits are machine 378, and the last 12 bits are sequence 0: the first ID that machine made in that millisecond.

A 64-bit ID is bigger than JavaScript's largest safe integer (253 − 1). Parse it as a number in a browser and the last digits get rounded. Send IDs to clients as strings, which is why Twitter's API returned both id and id_str.

Clock skew and monotonicity

Snowflake trusts the local clock, and clocks misbehave. Three cases matter.

Clocks differ between machines

NTP keeps servers in a datacenter within a few milliseconds of each other, but not exactly in step. An ID made on machine A can be smaller than one made a moment earlier on machine B. So Snowflake IDs are roughly time-ordered across machines (k-sorted), and strictly ordered only within one generator. Don't use them to decide which of two writes on different servers happened first; use a version number or a single sequencer for that.

The clock jumps backwards

NTP corrections, a VM migration or a bad manual change can move the clock back. If the generator carries on, it can repeat a timestamp it already used and, with the same sequence numbers, produce a duplicate ID. The usual rules:

  • Remember the last millisecond used. If the clock reads earlier, wait if the gap is small (a few ms) or refuse to issue IDs and alert if it's large.
  • Configure NTP to slew (speed up or slow down the clock gradually) rather than step it.
  • Read a monotonic clock for the "has time moved" check where your language offers one, and the wall clock only for the value.

Leap seconds

Large providers smear a leap second across many hours, so the clock never repeats a second. If you run your own NTP, do the same, or a whole second of timestamps can be issued twice.

A restart is a hidden backwards jump: the generator forgets the last millisecond it used. If a process can restart in under a millisecond with the same machine ID (rare, but possible with fast supervisors), persist the last timestamp or wait a few milliseconds on start-up.

Why sortable IDs help storage

Most databases keep the primary key in a B-tree, and in MySQL's InnoDB the table rows live in that tree too. Where a new key lands decides how much work an insert does.

  • Fewer page splits and fuller pages. Random inserts split pages in the middle and leave them about half full over time, so the same data takes more disk and more memory.
  • Better caching. Ordered inserts keep touching the same few pages. Random inserts need the whole index in the buffer pool, or each insert becomes a disk read.
  • Free time queries. "Newest first" is just ORDER BY id DESC, and an ID makes a stable pagination cursor (WHERE id < :cursor), as in the news feed.
  • Smaller everything. A 64-bit ID is 8 bytes; a UUID is 16. Every secondary index in InnoDB stores the primary key, so that difference is paid many times over.

The catch: on a range-sharded store (Bigtable, HBase, Spanner, CockroachDB), ever-increasing keys all go to the last range, which becomes a write hot spot. There, hash the key, put a shard prefix in front, or use a random ID. Hash sharding (Cassandra, DynamoDB) doesn't have this problem. See sharding.

How ID schemes fail

Two generators with the same machine ID

The most common real duplicate-ID bug. A config typo, a cloned VM or two pods with the same hostname suffix, and both make identical IDs in the same millisecond. Hand out machine IDs from something that enforces uniqueness: a lease in ZooKeeper or etcd that expires if the server dies, or a Kubernetes StatefulSet ordinal. Also keep the primary key constraint in the database, so a duplicate fails loudly instead of overwriting.

Sequence exhaustion

A burst bigger than the sequence space makes the generator wait for the next tick. With 12 bits that's 4,096 per ms, rarely a problem. With 8 bits and 10 ms ticks (Sonyflake) it's 25,600 a second per machine, which a busy service can hit.

Running out of time bits

A 41-bit millisecond timestamp lasts 69.7 years from your epoch. Pick a recent epoch, not 1970, or you've already used 56 of them.

The coordinator is down

Ticket servers and range leasing stop new IDs when the coordinator is unavailable. Lease bigger blocks, or lease the next block before the current one runs out, so a short outage goes unnoticed.

Leaking business data

Sequential IDs tell competitors how many orders you take per day: place two orders a day apart and subtract. Snowflake and UUIDv7 leak creation time. Neither should be the only thing protecting a private resource.

Saying it in an interview

"Writes are spread over many shards, so I don't want a central counter on the write path. I'd use 64-bit Snowflake-style IDs: 41 bits of milliseconds since our own epoch, 10 bits of machine ID, 12 bits of sequence. That's 70 years, 1,024 generators and 4,096 IDs per millisecond each. Machine IDs come from leases in etcd, so two servers can't share one. The generator refuses to issue IDs if the clock goes backwards. IDs are roughly time-sorted, so inserts append to the B-tree and the ID doubles as the feed cursor. We send them to clients as strings. If we needed unguessable public links, I'd add a separate random token rather than expose the ID."

Expect the follow-ups: what happens when the clock jumps back, how you assign machine IDs, whether IDs are strictly ordered across machines (no), and why not just use UUIDs (twice the size, and v4 is bad for B-trees).
