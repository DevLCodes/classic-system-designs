Classic system design walkthrough

Collaborative Document Editor

Design a document editor like Google Docs where several people type in the same document at once. Everyone sees the others' edits and cursors within a fraction of a second, nobody's typing is lost, and every screen ends up with exactly the same text. People can keep editing offline, leave comments, and share with different permissions. Plan for 100 million daily users and 5 million editing sessions open at peak.

Requirements

The hard part is not storing documents. It is letting two people change the same sentence at the same moment and have every screen agree on the result, without making anyone wait for the network before their letter appears.

Estimates

  • Back of the envelope
  • Numbers
  • Sessions: 100M users × ~30 minutes in a document a day = 3B user-minutes ÷ 1,440 ≈ 2.1M sessions open on average, ~5M at the daily peak.
  • Edits: about 1 in 5 open sessions is typing at any moment, and a client sends a batch of keystrokes roughly every 500 ms while typing: 2.1M × 0.2 × 2 ≈ 830k batches a second on average, ~2M at peak.
  • Operation log: 830k/s × 86,400 s ≈ 72B operations a day. At ~200 bytes each (document, revision, author, time, payload) that is ~14 TB a day before compaction.
  • Documents: 5B documents at ~50 KB of text and formatting ≈ 250 TB of latest snapshots, ×3 for replicas. History is kept as compacted revisions, not every keystroke.
  • Servers: 5M connections ÷ 50k per gateway ≈ 100 gateways. 2M batches/s ÷ ~20k per session server ≈ 100 session servers, each owning ~40k open documents at ~100 KB of memory each (≈ 4 GB).

API and protocol

  • Interface
  • WebSockets
GET  /api/docs/{doc_id}                     → { snapshot, rev: 1200, ops_since_snapshot: [...] }
WS   /ws/docs/{doc_id}                      (one socket per open document tab)

client → server
  { type: "op", client_id: "c9", seq: 17, base_rev: 1241,
    ops: [{ retain: 4 }, { insert: "team " }] }
  { type: "cursor", pos: 9, sel_end: 9 }    (throttled, never stored)

server → client
  { type: "ack", seq: 17, rev: 1242 }
  { type: "op", rev: 1243, author: "bob", ops: [...] }     (already transformed)
  { type: "presence", users: [{ id, name, colour, pos }] }

POST /api/docs/{doc_id}/comments  { anchor: {start, end, rev}, text }
PUT  /api/docs/{doc_id}/acl       { user, role: owner | editor | commenter | viewer }

An operation describes a change, not a new copy: keep 4 characters, insert "team ", keep the rest. base_rev says which version the user was looking at, and (client_id, seq) makes a resent operation safe to apply twice. A client has at most one batch in flight; while it waits for the ack it buffers new keystrokes into the next batch.

Architecture

  • Whole system

OT vs CRDTs

  • Deep dive 1
  • Consistency
  • Conflicted copies in file sync

Alice and Bob both look at revision 41: "The meeting…". Alice types "team " at position 4; Bob types "weekly " at position 4. If Alice's screen applies Bob's edit at position 4 as sent, and Bob's applies Alice's at 4, the screens disagree. Something has to adjust positions.

Operational transformation (OT)CRDT (conflict-free replicated data type)
IdeaOperations use positions. Before applying a concurrent operation, shift it past the ones that happened first.Every character gets a unique id. Inserts say "after character 4·alice", deletes say "hide 7·bob". Any order of applying gives the same result.
Needs a server?In practice yes: one server per document picks the order (rev numbers), and clients transform against itNo: peers can merge in any order, which suits offline and peer-to-peer
CostSmall operations, no per-character metadata; transform code is subtle to get rightIds and tombstones for every character ever typed; modern libraries (Yjs, Automerge) compress this well
Used byGoogle Docs (descended from the Jupiter and Google Wave designs)Many newer editors and local-first apps

For an interview, pick one and say why. A Google Docs style product already has a server in the middle for permissions, history and fan-out, so OT with a central session server is the simple, proven choice; this page uses it. Reach for a CRDT when long offline periods or peer-to-peer sync are core requirements. Either way, both algorithms merge characters, not meaning: if two people rewrite the same word, both versions survive, and people fix the sentence.

How it works: each person's change is found by comparing their text with the start (one replaced span), then split into one-character inserts and deletes. OT transforms each list against the other, with Alice winning ties. The CRDT is a small RGA: each character has an id (counter, author), and inserts point at the character to their left.

One session server per document

  • Deep dive 2
  • Sharding
  • Leases
  • Why one owner: OT needs a single agreed order. Giving each document exactly one session server makes that order trivial: the server's revision counter. With ≤ 100 live editors and ~10 batches a second even in a busy document, one core handles it easily.
  • Finding the owner: a document's owner is recorded as a lease in a coordination store such as etcd or ZooKeeper (doc_7f3 → session-42, expires in 10 s). Gateways cache the lookup. Consistent hashing picks a default owner, and the lease makes sure two servers never both think they own it.
  • Server loop: receive op with base_rev → transform it against every op since base_rev (kept in memory) → assign the next rev → append to the op log → ack the author and broadcast to everyone else.
  • Client loop: apply your own typing instantly, keep one batch in flight and buffer the rest. When a remote op arrives, transform it against your in-flight and buffered ops before applying, and transform those against it.
  • Failover: if a session server dies, its leases expire after ~10 s and other servers take over its documents: load the latest snapshot, replay the log tail, start accepting. Clients reconnect and resend their in-flight batch; (client_id, seq) already in the log means it is acked without applying twice.
  • Moving hot or idle documents: idle documents are unloaded after a few minutes with no one connected. A server near capacity hands documents off by releasing the lease after its last append.

Presence and cursors

  • Deep dive 3
  • Presence in chat
  • Who is here: the session server already holds every connection for the document, so presence is just its in-memory list of sessions with a name and a colour. No database, no TTL keys: if the socket drops, the person disappears from the list.
  • Cursors are positions too: Bob's caret at position 12 must move to 17 when Alice inserts 5 characters before it. Clients transform remote cursors through each operation exactly like an insert of zero length.
  • Throttle and drop: cursor and selection updates are sent at most every ~100 ms while moving, carry the rev they refer to, and are never logged. A lost cursor update is harmless; the next one replaces it.
  • Cost: cursor messages can outnumber edits, so they share the socket but skip the op log and the transform queue. In a 100-person document, the server batches them into one presence message every ~200 ms instead of 99 separate ones.

Operation log and snapshots

  • Deep dive 4
  • Logs
  • Databases

The log is the document. A snapshot is just a cached result of replaying it, so you never have to replay from revision 1.

  • Append before ack: an op is acknowledged only after it is durably written as row (doc_id, rev) in a replicated store such as Bigtable, Cassandra or Spanner. The write is conditional on the rev not existing yet, which also catches a second server that wrongly believes it owns the document.
  • Batching: the server groups appends from many documents into one write every few milliseconds, so ~20k ops a second need only hundreds of storage writes.
  • Snapshots: every 500 ops (or after a minute idle), a snapshotter replays the log onto the last snapshot and writes the whole document to blob storage as doc_id/rev. Opening a document = one snapshot read + at most 500 ops.
  • Version history: "see older versions" reads snapshots plus ops. After about a week, keystroke-level ops are compacted into revisions a few minutes apart, cutting the ~14 TB a day by around 100×.
  • Checksums: every few hundred ops the server sends a hash of the text at a rev. A client whose own hash differs has diverged (a bug), throws away its copy and reloads from the server.
open cost = 1 snapshot (~50 KB) + up to 500 ops × 200 B ≈ 150 KB worst case

Offline edits

  • Deep dive 5
  • Sync by cursor
  • Keep working: the client stores the document and every unacknowledged op in IndexedDB, tagged with the last rev it saw. Typing never needs the network.
  • Reconnect: the client sends its pending ops with that old base_rev. The server transforms them against everything that happened since, which for a few hours of edits is thousands of cheap transforms, and sends back the ops the client missed.
  • Long gaps: if the server has already compacted the ops the client needs (say after a week away), it cannot transform. Fall back to a three-way text merge against the snapshot at that rev, or save the offline work as a separate version and show it in history. This is where CRDTs shine: they merge any two replicas without keeping the server's history.
  • Surprises: merged offline work can read oddly (two people rewrote the same paragraph). Mark it in version history as "edits made offline by Bob" so people can review or restore.

Permissions and comments

  • Governance
  • Roles: owner, editor, commenter, viewer, plus "anyone with the link". The docs service stores the ACL with the document's metadata in a strongly consistent database.
  • Check on join and on every op: the gateway checks the role when the socket opens; the session server checks the op type (a commenter may send comment and suggestion ops, never text ops). The server validates every op against the document length, so a bad client cannot corrupt it.
  • Revocation: when an editor is removed, the ACL change is pushed to the session server, which closes that person's socket at once instead of waiting for a token to expire.
  • Comments: stored in their own table by doc_id, with an anchor (start, end, rev). The anchor is transformed through later ops just like a cursor, so the comment stays on its words; if the words are deleted, the comment shows as detached.
  • Suggestions: "suggesting" mode sends normal ops marked as suggestions. Accepting one turns it into a normal op; rejecting sends the inverse.
  • Notifications: @mentions and replies go through Kafka to an email and push service, never on the edit path.

Deployment and regions

  • Production
  • Home region per document: a document's session server runs in one region, usually near its owner. Editors elsewhere connect to a nearby gateway, which forwards to the home region over the backbone: ~100–150 ms extra across oceans, hidden by local echo.
  • Move with the crowd: if most active editors are in another region, hand the lease over at a quiet moment.
  • Durability: the op log is replicated across zones before ack; snapshots are copied to a second region.
  • Deploys: drain a session server by releasing its leases one by one; clients see a reconnect of a second or two and resend their in-flight batch.

v2 ideas: a CRDT engine for true offline-first and peer-to-peer, live tables and embedded charts with their own operation types, AI suggestions that arrive as suggestion ops, and end-to-end encrypted documents (the server then orders encrypted ops without reading them, which favours CRDTs).

"Every client applies its own typing immediately and sends small operations tagged with the revision it was based on. Each document has exactly one session server, found through a lease, and that server is the single place that orders edits: it transforms a late operation past the ones it already accepted, gives it the next revision, appends it to a durable log, then acks the author and broadcasts it. Clients transform incoming operations against their pending ones, so everyone converges. Snapshots every 500 operations keep opens fast, presence and cursors live in the session server's memory, and offline edits are just pending operations with an old base revision. I'd pick OT because we already have a server in the middle; a CRDT is the choice if peer-to-peer or long offline periods matter more."
