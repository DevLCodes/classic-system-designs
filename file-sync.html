File Sync

Design a file storage and sync service like Dropbox or Google Drive. Users upload and download files from any device, and changes made on one device appear on their other devices automatically. Files can be as large as 50 GB, uploads must survive dropped connections, and files must never be corrupted or lost.

Requirements

  • Clarify
  • Non-functional requirements

The core entities are just files (raw bytes), file metadata and users. The difficulty is moving as few bytes as possible, keeping many devices in step, and never losing or corrupting anything.

Out of scope: building our own blob storage (we use S3 or similar), real-time collaborative editing (that's Google Docs, a different design) and full-text search inside files.

Estimates

  • Back of the envelope
  • Numbers
  • Storage: 500M accounts averaging ~2 GB is about 1 EB before dedupe. Identical blocks across users (the same installer, the same PDF) are stored once, which saves a meaningful share.
  • Changes: 100M daily users × ~10 file changes ≈ 1B a day ≈ 12k a second, peaking around 3× during working hours.
  • Bytes: most changes are small edits to existing files. If each uploads ~100 KB of new blocks on average, that is 100 TB a day of new data, about 10 Gb/s.
  • Metadata: 1 EB in 4 MB blocks is 250 billion block references. Each is a 32-byte hash plus a little bookkeeping: tens of TB of metadata, which must be sharded.

Uploading is a two-step handshake: ask which blocks are missing, upload just those, then commit the new list of hashes with the revision the client started from. Downloads work the same way in reverse. Presigned URLs keep file bytes off our API servers, and a 50 GB upload is just 12,500 independent, retryable block uploads.

Architecture

  • Whole system
  • Client: watches the sync folder, splits changed files into blocks, hashes them, and keeps a local database of what it believes the server has. Most of the cleverness lives here.
  • Metadata service: the source of truth for files, folders, revisions and which blocks make up each revision.
  • Block store: immutable blocks keyed by their hash, in object storage.
  • Notification service: holds a connection per online device and nudges it when its account's journal moves.

Blocks, hashes and dedupe

  • Deep dive 1
  • Hashing

Never upload a whole file twice. Split it into blocks, name each block by the hash of its content, and only send blocks the server doesn't have.

  1. Split each file into blocks (Dropbox uses 4 MB).
  2. Hash each block with SHA-256. The hash is the block's name, its dedupe key and its integrity check.
  3. Ask the server which hashes are missing. A small edit to a large file usually changes one block; copying a file the server already has (even from another user) uploads nothing.
  4. Upload the missing blocks in parallel; each is retried independently, so a 50 GB upload resumes where it stopped.
  5. Commit the new revision as an ordered list of hashes. The server verifies every block exists and matches its hash before accepting.

Fixed or content-defined blocks?

Fixed 4 MB blocks have a weakness: insert one byte near the start of a file and every block boundary after it shifts, so every block hash changes. Content-defined chunking places boundaries where a rolling hash of the content hits a pattern, so boundaries move with the content and an insert changes only the block it lands in. rsync-style tools and backup systems use this; the lab shows the difference.

Cross-user dedupe leaks information. If uploading a file finishes instantly, the uploader learns someone already has it. Services often limit dedupe to within an account or a team, or always accept the upload for blocks they could otherwise skip.

Keeping devices in sync

  • Deep dive 2
  • Long polling
  • Logs

Each account (or shared folder) has an append-only journal of changes with increasing sequence numbers. A device only needs to remember the last number it has applied: its cursor.

  1. A commit writes the new revision and appends (seq 1042, path, rev 42, block_hashes) to the account's journal in the same transaction.
  2. The notification service sees the journal move and tells every online device of that account: "there are changes", nothing more.
  3. Each device calls GET /changes?cursor=1037, gets entries 1038–1042, downloads any blocks it lacks, applies them, and stores cursor 1042.
  4. An offline device does exactly the same when it comes back, however long it was away. If the journal was compacted past its cursor, it falls back to a full listing and compares.

Dropbox's desktop client used long polling for years: a request that hangs for up to a minute and returns as soon as something changes. WebSockets work too. Either way the notification carries no data, so a lost notification only delays sync until the next poll; the journal is what guarantees nothing is missed.

Client-side state is what makes this robust: the client keeps a local database of the server's view (path, rev, hashes) and its own view of the disk, and reconciles them. Most sync bugs are disagreements between those two views, which is why Dropbox rewrote its sync engine around a strict three-tree model (local, remote, synced base).

Conflicts

  • Deep dive 3
  • Consistency

Every commit says which revision it was based on (parent_rev). The metadata service accepts it only if that is still the latest revision: a compare-and-set. If not, two devices edited the same file concurrently and the server returns a conflict.

For arbitrary files we can't merge automatically (what does merging two Photoshop files mean?), so the losing client saves its version as report (Asha's conflicted copy 2026-11-10).docx next to the winner. No data is lost and the user decides. Last-writer-wins would be simpler and would silently throw away someone's work, which is unacceptable for a storage product.

Storage

  • Databases
  • Sharding
namespaces   (ns_id, owner_id, type: user | shared_folder)
files        (ns_id, file_id, path, latest_rev, is_deleted)          PK (ns_id, file_id)
revisions    (ns_id, file_id, rev, parent_rev, size, mtime, block_hashes[], author)
journal      (ns_id, seq, file_id, rev, op)                          PK (ns_id, seq)
blocks       (hash PK, size, storage_key, ref_count)
  • Metadata needs transactions (commit a revision and append to the journal together, compare-and-set on latest_rev), so it lives in a relational database, sharded by namespace id. Dropbox ran this on sharded MySQL (its Edgestore layer) for years.
  • Blocks are immutable and content-addressed, so they are trivially cacheable and replicable. Dropbox moved from S3 to its own system, Magic Pocket, at exabyte scale; for us, S3 or another object store is right.
  • Garbage collection: deleting a file doesn't delete blocks, which may be shared. Keep a reference count (or periodically mark blocks reachable from live revisions) and delete unreferenced blocks after the version-history window, often 30 days or more.

Sharing and security

  • Governance
  • Shared folders are namespaces. Each member's tree mounts the shared namespace at some path. Commits go to the shared namespace's journal, and every member's devices follow it.
  • Permissions are checked by the metadata service on every call; presigned block URLs expire in minutes and are only issued after the check.
  • Links ("anyone with the link") are random tokens with optional expiry and passwords, revocable at any time.
  • Encryption: TLS in transit, encryption at rest per block. End-to-end encryption is possible but breaks server-side previews, search and cross-user dedupe.

Deployment and durability

  • Production

Blocks are stored with replication or erasure coding across availability zones, plus asynchronous copies to a second region. Metadata shards run with synchronous replicas in another zone and asynchronous replicas in another region, and point-in-time backups. The API and notification tiers are stateless and run in several regions; block uploads go to the nearest region's endpoint.

Verify everything, always. Hash blocks on the client before upload, verify on the server after upload, store the hash with the block, re-verify on download, and scrub stored blocks in the background. A storage service is judged on the bug it never has.

"I'd separate metadata from bytes. The client splits files into 4 MB blocks named by their SHA-256, asks the metadata service which ones are missing, uploads only those straight to S3 with presigned URLs, and commits a new revision as a list of hashes with the revision it started from. That makes uploads resumable, dedupes identical content and makes small edits cheap. Each account has a change journal; devices keep a cursor, get a 'something changed' push or long-poll response, fetch entries since their cursor and download missing blocks. Commits are compare-and-set on the parent revision; on a conflict the client keeps both versions as a conflicted copy, so no edit is ever lost."
