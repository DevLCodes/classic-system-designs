Nearby Places

Design a service like Yelp: given where the user is, find restaurants, cafés and other places within a radius, filtered by category and ranked well, with reviews, ratings and photos. There are 500 million places, growing 20% a year, and 100,000 searches a second.

Requirements

  • Clarify
  • Non-functional requirements

Places change rarely and searches are constant, so the design is a read-optimized spatial index kept close to the search servers, with a normal database behind it.

QuestionAssumptionWhy it matters
Places500M, +20% a yearIndex size and growth
Searches100k a second, +20% a yearRead capacity; peaks around meal times
WritesAdd, update, delete places; a few hundred a secondIndex can lag by minutes
QueryLocation + radius, optional category, open now, price, sortSpatial lookup first, then filters and ranking

Out of scope: turn-by-turn directions, reservations and ads.

Estimates

  • Back of the envelope
  • Numbers
  • Place record: id (8 B), name (256 B), latitude and longitude (8 B each), description (512 B), category (1 B) ≈ 793 bytes. 500M × ~800 B ≈ 400 GB, growing 20% a year. Fine for a sharded relational database.
  • Geo index: only id, latitude and longitude: 24 bytes × 500M = 12 GB, perhaps 20–30 GB with tree overhead. It fits in RAM on one machine, so every search server can hold a full copy.
  • Search capacity: a lookup plus ranking costs a few ms of CPU. At ~2,000 searches a second per server, 100k a second at a 3× peak needs about 150 servers, spread across regions.
  • Reviews: if places average 4 reviews, 2B reviews × ~600 B ≈ 1.2 TB of text. Photos are far larger and live in object storage behind a CDN.

Search is the one that matters. The page token encodes the query and the last result's score, so paging is stable even while the user scrolls. Clients round the location a little (to ~50 m) before searching, which makes nearby users' queries identical and cacheable for a few seconds.

Architecture

  • Whole system

Finding what's nearby

  • Deep dive 1
  • Indexes

A normal B-tree index sorts on one dimension. "Near here" is two-dimensional, so we need a way to turn locations into keys that keep nearby places close together.

ApproachHowProblem
Plain SQLWHERE lat BETWEEN x−d AND x+d AND lng BETWEEN y−d AND y+dAn index helps one column only; the database scans a huge strip of the world for the other
Fixed gridCut the world into equal cells (say 10 miles), store grid_id with each place, search the cell and its 8 neighboursCells in Manhattan hold thousands of places; cells in the ocean hold none. Fixed size fits nowhere well. The index is ~4 GB for 20M cells and 500M places
QuadtreeStart with one cell for the world; split any cell with more than ~500 places into four, recursivelyCells are small where places are dense and large where they're sparse. Built in memory; needs rebuilding or careful updates
GeohashInterleave latitude and longitude bits into a string; a shared prefix means a shared cell (dr5ru ≈ 5 km)Works in any database with a string index; neighbours across a prefix boundary need extra lookups
S2 or H3 cellsHierarchical cells on a sphere (squares for S2, hexagons for H3) with 64-bit idsBest general choice today; the libraries handle covering a circle with cells. See Ride matching
PostGIS, Elasticsearch geoR-trees or BKD trees built into the database or search engineGreat up to a few hundred million points with filters and full text combined

How a quadtree search works

  1. Walk from the root to the leaf containing the user's location (about log4(500M ÷ 500) ≈ 10 levels).
  2. Collect every leaf whose box intersects the search circle: walk the tree, skipping any branch whose box misses the circle. Linking leaves or keeping parent pointers makes neighbours cheap to find.
  3. Check each place in those leaves against the exact distance, and keep the ones inside the radius.
  4. If there are too few results, widen the radius and repeat.

Try it: a quadtree

  • Lab

800 places in three dense neighbourhoods and some countryside. Click or tap the map to move the search, change the radius, and change how many places a cell may hold before it splits. Compare the work with a fixed grid.

The fixed grid uses equal cells of 100 × 100 units and checks every cell that overlaps the circle's bounding box. Map units are arbitrary; at city scale one unit is about 10 m.

Filtering and ranking

  • Deep dive 2

The spatial lookup returns candidates, typically a few hundred to a few thousand ids. The search service then:

  • Filters on attributes kept alongside the ids in memory: category, price level, a bitmap of opening hours, so "open now" needs no database call.
  • Scores each candidate: distance, rating (smoothed, so 5 stars from 3 reviews doesn't beat 4.6 from 800), popularity, and text match if there is a query like "ramen".
  • Takes the top 20 and only then hydrates details from the cache.

Text search and filters on many attributes are where Elasticsearch or OpenSearch shine: they combine a geo filter, full text and scoring in one query. A common design is exactly that, with the custom in-memory index reserved for the very hottest, simplest queries.

Popular areas: results for "restaurants near Times Square" are the same for thousands of users a minute. Rounding locations and caching results per (cell, filters) for 30–60 seconds takes a large share of load off the index.

Storage

  • Databases
  • Caching
places                        (MySQL/Postgres, sharded by place_id)
  place_id  bigint PK   name  varchar(256)   lat, lng  double
  category  smallint    description text     hours  json   status

reviews                       (Cassandra, partitioned by place_id)
  place_id  bigint      review_id timeuuid   user_id, rating, text, photo_ids

place_stats                   (Redis + periodic rollup)
  place_id → { rating_avg, review_count, popularity }

Places are relational and modest in size: a sharded SQL database with read replicas. Reviews are append-heavy and read newest-first per place: a wide-column store. Rating averages are maintained incrementally and cached, never computed from raw reviews on a search.

Sharding and replicas

  • Deep dive 3
  • Sharding

At 12–30 GB the index fits on one machine, so the simplest design is full replicas: every search server holds the whole index, and any server answers any query. That stops working when the index or its attributes outgrow memory, or rebuilds become too slow.

Shard byUpsideDownside
Region or cityA query touches one shardHot cities make hot shards; queries near a boundary need two
Place id (hash)Even size and loadEvery query fans out to every shard and the results are merged

Hashing by place id with an aggregator is the usual choice once sharding is needed: each shard returns its own top-k for the area, and the aggregator merges them. Tail latency then depends on the slowest shard, so send a hedged request to a replica when one shard is slow.

Keeping the index fresh

Place changes are captured from the database (change data capture) onto Kafka. Each search server applies the deltas to its in-memory index, and a nightly snapshot lets new or restarted servers load a full index in minutes instead of rebuilding from the database. A crashed server restarts from the snapshot plus the Kafka log since.

Reviews and trust

  • Governance
  • Rate limiting
  • Fake reviews are the main abuse: businesses praising themselves or attacking rivals. Score reviews with signals (account age, location history, bursts of reviews for one place, text similarity) and hide suspicious ones from the rating.
  • Photos go to object storage via presigned uploads, are scanned and resized asynchronously, and are served from a CDN.
  • Wrong data (closed places, wrong pins) is reported by users and verified, then fed back through the normal write path.

Deployment

  • Production

Search runs in several regions, with users routed to the nearest by latency-based DNS. Each region holds full index replicas, so a region failure only shifts traffic. The places database has one primary region with replicas elsewhere; writes are rare and can tolerate the extra distance. Search servers are stateless apart from the index they load at start, so they autoscale on CPU, with a warm-up step that loads the snapshot before taking traffic.

v2 ideas: personalized ranking, search along a route, reservations and ordering, and indoor or venue-level maps.

"Searches outnumber writes by hundreds to one, so I'd build a read-optimized geo index next to the search servers. A plain SQL range query can't use an index on two dimensions, and fixed grids are wrong in both cities and countryside, so I'd use a quadtree that splits any cell above about 500 places, or S2 cells in production. The index only holds id, latitude, longitude and a few filter fields: about 12 GB, so every search server keeps a full copy in memory. A search walks to the cells overlapping the circle, filters and ranks a few hundred candidates, and hydrates the top 20 from Redis. Place edits flow from the database through CDC and Kafka into the index within minutes."
