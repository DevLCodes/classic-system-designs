Hot partitions, sub-sharding and write buffering

What to do when one key gets more traffic than a whole shard can take, even though your hash spreads every other key evenly.

How hot keys happen

Hashing spreads keys evenly. It does nothing for traffic that piles onto one key. Every write for that key goes to the same shard, so adding shards does not help.

Common sources of hot keys:

  • Celebrities and viral items. A star's profile, a post with millions of likes, a product on a flash sale. Traffic follows people, not hashes.
  • Counters. One like count or view count that every request increments. Each increment is a write to the same row.
  • Time-ordered keys on range shards. If the key starts with a timestamp or an auto-increment ID, all new writes land on the last range. See range vs hash.
  • Big tenants. In a multi-tenant system keyed by tenant_id, one large customer can outweigh thousands of small ones.
  • Default values. A key like country=unknown or user_id=0 that a bug or a missing field sends everything to.

To act on hot keys you first have to find them. Shards can count requests per key and report the top few (a heavy-hitters sketch such as count-min keeps this cheap). Managed stores expose it too: Redis has redis-cli --hotkeys when using an LFU policy, and DynamoDB has CloudWatch Contributor Insights.

A hot key is a per-key limit, not a cluster limit. In DynamoDB each partition serves at most 3,000 reads and 1,000 writes per second (in capacity units). A table can take millions of writes a second while one key is throttled at 1,000.

Key salting

The simplest fix is to split one logical key into k physical keys by adding a suffix, often called a salt. Writes pick one suffix; reads gather all of them and merge.

Random or calculated suffix

SuffixHow it is pickedGood forCost
Randomrand() % k on every writeCounters and append-only data where you always read the totalReading one item means reading all k sub-keys
CalculatedFrom another field, like hash(user_id) % k"Did user 42 like post 123?": you know which sub-key to checkSpread is only as even as that field; one heavy user still lands on one sub-key

Merging reads

How you merge depends on the data. A counter sums the sub-counts. A list, such as comments on a post, needs a k-way merge by timestamp, then a limit. A set unions the parts, or checks just one part when the suffix is calculated. Merging is only cheap if each sub-read is cheap, so keep the parts small and read them in parallel.

writes per sub-key = W / k  ·  reads per key read = k  ·  P(read waits on a slow part) = 1 − (1 − p)k

The last formula is why you do not salt every key. If 1% of reads to any one shard are slow (p = 0.01), a read that touches 16 parts hits a slow one about 15% of the time. Salting moves the hot spot off writes and puts a tail-latency tax on reads.

Dynamic sub-sharding

Salting everything wastes read capacity on the millions of keys that are never hot. The better pattern splits keys only when they get hot and folds them back when they cool.

  1. Detect. Each shard counts writes per key over a short window. A key above a threshold, say half of one shard's capacity, is flagged.
  2. Publish the split. Write key → k to a small split table (in a config store like etcd or ZooKeeper, or a tiny replicated table). Clients cache it.
  3. Readers first, then writers. Readers must start reading all k parts before any writer uses part #k−1, or a reader will miss data. Roll the change out to readers, wait for the cache TTL, then let writers spread.
  4. Grow by doubling. Go 1 → 2 → 4 → 8 while the key stays hot. Placing parts on different shards matters more than the number: beyond one part per shard, more parts add read cost without spreading writes further.
  5. Merge back. When the key cools, stop writing to the high parts, fold their values into part #0, keep readers reading all parts for a grace period, then drop the entry.

Some stores do this for you at the partition level. DynamoDB's adaptive capacity can isolate a hot item and split a partition "for heat", and Bigtable and Spanner split ranges by load. None of them can split a single item that one key maps to; that part is always your job.

Try it: a celebrity key

Eight shards, each rated for 1,000 writes a second, already carry 300 writes a second of normal traffic. One celebrity key gets a burst of writes. Split it into sub-keys, and optionally put a write-ahead buffer in front.

4 aggregator workers

Sub-keys are placed one per shard, wrapping around after eight. The slow-read odds assume 1% of reads to any one shard are slow and that the key's parts are read in parallel. With the buffer on, each worker sends one combined write per sub-key it touched per flush. The red tick on each bar is the 1,000 writes/s capacity.

Write-ahead buffering

Salting spreads writes. Buffering removes them. Instead of writing each like straight to the database, append it to a durable log, then let a small set of workers read the log, add up changes per key, and write one combined update per flush.

  • Durability comes from the log. The write is acknowledged once it is in the replicated log, so a worker crash loses nothing: a new worker replays from the last committed offset.
  • Replays must be safe. A worker can crash after writing to the database but before committing its offset. Store the last applied offset with the row, or make the update idempotent, so the replay is skipped instead of counted twice. See queues.
  • It fits commutative updates. Increments, appends and set-adds can be combined in any order. "Set price to X" or "reserve the last seat" cannot be batched blindly; those need a single writer or a transaction.
  • It is the same idea as an LSM tree or a write-back cache, one level up: absorb writes in a fast append-only structure, then fold them into the slow store in batches. See databases and write-back caching.

Read-your-writes trade-offs

Both fixes make it harder for someone to see their own change right away. Pick per feature, not for the whole system.

TechniqueWhat a reader seesFix if users notice
Salting, strong readsExact, once all k parts are readNothing to fix, but each read costs k
Salting, replica readsEach part can lag by a different amountRead the writer's own part from the leader
Write-ahead bufferUp to one flush window plus log lag behindOverlay the user's own pending change in the app ("you liked this", count + 1)
Buffer plus a cacheA cached total, refreshed every few secondsShow approximate numbers ("1.2M likes"), which nobody can check

For a like counter, a few seconds of lag is invisible. For a bank balance or seat inventory, it is a bug. Those keys are rarely hot in the celebrity sense, and when they are (a flash sale), the answer is a queue in front of a single writer, as in ticket booking, not batching.

How it goes wrong

Stale split table

A writer that learned k=8 before a reader that still thinks k=4 puts data in parts the reader never reads. Always widen readers before writers, and narrow writers before readers.

Sub-keys on the same shard

With plain hashing, two sub-keys can land on the same node and you get less spread than k suggests. Check where parts land, or place them through a directory.

The hot spot moves

Key the log by the hot key and one log partition takes all the traffic. Cache the hot key in one Redis node and that node melts instead. Every layer on the path needs its own spread.

Read amplification

Salting a key read 50,000 times a second into 16 parts creates 800,000 sub-reads a second. Pair it with a short-lived cache of the merged result, or the read side becomes the hot spot.

Lost or double counts

Buffered counters drift if replays double-apply or a worker drops a batch. Run a periodic job that recounts from the log or source rows and corrects the total.

Saying it in an interview

"Likes are keyed by post ID, which spreads well until a post goes viral. One shard handles about 1,000 writes a second, and a viral post can see 20,000. I'd do two things. First, writes go to a Kafka topic partitioned by event ID, and four aggregators sum likes per post and flush every 100 ms, so the database sees about 40 writes a second for that post no matter how many likes arrive. Second, for keys still too hot, a detector adds them to a split table and we salt them into up to 8 sub-keys, one per shard; readers sum the parts, and we cache the total for a few seconds. The trade-off is that a liker might not see their own like in the count for a moment, so the app adds it locally."
