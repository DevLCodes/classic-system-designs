Threads, locks and wait/notify

How one Java program does two things at once: a background thread waits for work, other threads hand it work, and one lock keeps them from trampling each other.

What a thread is

A thread is one line of execution: it runs one statement after another. A Java program starts with one thread, main. Every extra thread you start runs its own code at the same time, inside the same program.

Use a thread when work must happen in the background while the caller carries on. Examples are a task that should run in 5 seconds, a server handling many requests at once, or a slow file write that shouldn't freeze the program.

The rest of this page uses one small example: a delayed task runner. Callers say "run a task in N ms" and return at once. One background worker thread keeps the tasks in a min-heap ordered by due time and runs each when it is due.

class DelayedRunner {
    // due times in ms, earliest on top (a min-heap)
    private final PriorityQueue<Long> due = new PriorityQueue<>();

    void init() {
        Thread worker = new Thread(this::loop, "worker");
        worker.setDaemon(true);
        worker.start();
    }

    synchronized void schedule(long delayMs) {
        due.add(System.currentTimeMillis() + delayMs);
        notify();
    }

    private synchronized void loop() {
        try {
            while (true) {
                if (due.isEmpty()) { wait(); continue; }
                long left = due.peek() - System.currentTimeMillis();
                if (left > 0) { wait(left); continue; }
                due.poll();
                System.out.println("Task ran");
            }
        } catch (InterruptedException e) { /* asked to stop */ }
    }
}

Every line in it is there for a threading reason. The next sections take them one at a time.

Starting a thread

new Thread(...) creates an object, not a thread

new Thread(this::loop) builds a Thread object and remembers which code to run. Nothing runs yet. The thread is in the NEW state.

start() launches it, run() does not

start() asks the JVM and the operating system for a real new thread with its own stack. That new thread calls your code. start() itself returns straight away, so the caller and the new thread now run side by side. You can call start() only once per Thread object.

setDaemon(true): don't keep the program alive for me

The JVM exits only when every non-daemon thread has finished. New threads are non-daemon by default. Our worker loops forever, so without setDaemon(true) the program would never exit. Call it before start(); calling it afterwards throws IllegalThreadStateException.

Shared data and locks

The problem: a race condition

Even count++ is three steps: read the value, add one, write it back. If two threads interleave those steps, one update is lost. A heap is far worse: two threads adding at once can leave it corrupted.

The fix: synchronized

Every Java object has one built-in lock, called its monitor. A synchronized method takes the lock of this on the way in and gives it back on the way out, even if it throws. Only one thread can hold a lock at a time, so only one thread is ever inside schedule() or loop(), and the heap is never touched by two threads at once.

Lock what you share, and nothing more. Every read and every write of the shared heap happens inside synchronized on the same object. A lock only protects data if every thread that touches the data takes that same lock.

wait() and notify()

The worker needs to sleep until the next task is due, but wake up early if someone adds a task that is due sooner. Neither a lock nor sleep() can do that; wait() and notify() can.

  • wait() releases the lock and sleeps. When it wakes, it takes the lock back before returning. Releasing the lock is the whole point: it lets schedule() get in while the worker sleeps.
  • wait(ms) does the same, but also wakes by itself when the time is up.
  • notify() wakes one thread waiting on this object. notifyAll() wakes all of them. Use notifyAll() when several threads wait for different reasons.
  • All three must be called while holding that object's lock, inside synchronized. Otherwise Java throws IllegalMonitorStateException.

Always re-check in a loop

Waking up tells you something happened, not what. It could be a notify for a task due in an hour, a timeout, or a spurious wakeup (the JVM may wake a waiting thread for no reason). So every wait() sits inside a while loop that re-checks the condition, which is why loop() says continue after each wait.

// wrong: assumes waking up means "the task is due"
if (left > 0) wait(left);
due.poll();                         // may run a task early

// right: wake, then check again
while (true) {
    long left = due.peek() - now();
    if (left > 0) { wait(left); continue; }
    due.poll();
}

    Saying it in an interview
    

    "I'd start one daemon worker thread in init() with start(). Scheduled items go into a min-heap of absolute due times, so the next one is an O(1) peek and inserts are O(log n). schedule() and the worker loop are both synchronized on the same object, so the heap is never touched by two threads at once. The worker waits with wait(timeLeft), which releases the lock, and schedule() calls notify() so a new, earlier item wakes it. After every wake it loops and re-checks the top, which handles notifies, timeouts and spurious wakeups. In production I'd use ScheduledExecutorService, which is built the same way."
    

    

    Why not just Thread.sleep(delay) in schedule()?
    It blocks the caller. The point is that the caller returns at once and a background thread does the waiting.
    

    Why not one new thread per task?
    Each thread has its own stack (around 0.5 to 1 MB reserved by default). Thousands of tasks waiting at once means thousands of threads. One worker with a heap waits on all of them for the cost of one.
    

    sleep() vs wait()?
    sleep() keeps every lock and can only be ended by time or an interrupt. wait() releases the object's lock and can be ended by notify().
    

    notify() vs notifyAll()?
    notify() wakes one waiter, which is enough when exactly one thread waits. With several waiters, or waiters for different conditions, notifyAll() is the safe choice.
    

    Why store now + delay and not the delay?
    A delay is relative to when the request arrived. The worker compares due times with the clock, so it needs absolute times. Prefer System.nanoTime() over currentTimeMillis() for this, as it never jumps when the wall clock is adjusted.
    

    What does volatile do, and do we need it here?
    It makes writes to a field visible to other threads at once. We don't need it here, because entering and leaving synchronized already makes changes visible to the next thread that takes the lock.
    

    How would you stop the worker cleanly?
    Keep a reference to it and call worker.interrupt(). A thread blocked in wait() or sleep() gets InterruptedException and leaves the loop.
    

    


    In the real world
    

    Hand-written wait() and notify() are for learning and interviews. Production code uses java.util.concurrent, which wraps the same ideas in safer tools.
