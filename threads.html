The big picture

A thread is a worker that runs code. Every program starts with one, main. You can start more, and they all run at the same time.

Think of a kitchen with one knife. Each thread is a cook. They all share the same food (your objects, like a PriorityQueue). The knife is the lock: only the cook holding it may touch the shared food.

Four ideas cover almost everything: how a cook starts, how the knife works, how cooks nap and wake each other, and which cooks Java waits for before closing the kitchen.

start() vs run()

start() hires a new cook who does the work. run() means you do the work yourself.

Thread t = new Thread(this::loop);
t.start();   // new thread runs loop(); this line returns at once
t.run();     // NO new thread: you run loop() yourself and get stuck
  • new Thread(...) only creates an object. Nothing runs until start().
  • You can call start() once per thread.

synchronized: one knife

To enter a synchronized block you must pick up the knife (the lock). If someone else has it, you wait. When you leave, the knife is put down for you.

synchronized (this) {   // pick up the knife (or wait for it)
    queue.add(x);       // only one thread here at a time
}                       // knife put down automatically

A synchronized method is the same thing, wrapped around the whole method. Why bother? If two threads change the same queue at the same moment, it can break. The lock makes them take turns.

wait() and notify()

What it saysWhat happens
wait()"Nothing to do yet. I'll nap."Puts the knife down and sleeps until notified. wait(ms) also wakes when time is up.
notify()"Wake up, something changed."Wakes one napping thread. It picks the knife back up, then checks again.

Both must be called while holding the knife, inside synchronized. Otherwise Java throws IllegalMonitorStateException.

In the alarm problem

synchronized void schedule(long delay) {
    due.add(now() + delay);
    notify();   // "new alarm, go check"
}

synchronized void loop() throws InterruptedException {
    while (true) {
        if (due.isEmpty()) { wait(); continue; }      // nap until notified
        long left = due.peek() - now();
        if (left > 0) { wait(left); continue; }  // nap until due, or notified
        due.poll();
        System.out.println("Alarm Triggered!!");
    }
}

Always continue after waking. Waking means "something happened", not "the alarm is due". Go back and check.

What about Thread.sleep()?

Thread.sleep(ms)wait() / wait(ms)
The knife while nappingKeeps itPuts it down
Woken early by notify()?NoYes
Needs synchronized?NoYes

If the alarm worker used Thread.sleep(5000) inside synchronized, it would hold the knife for 5 s. schedule(2000) could not get in, and the 2 s alarm would ring late. sleep() is fine when you hold no lock, like Thread.sleep(6000) in main.

Daemon threads

A daemon is a background helper. Java closes the kitchen when all the normal cooks are done. It does not wait for daemons.

Thread t = new Thread(this::loop);
t.setDaemon(true);   // must be before start()
t.start();

The alarm worker loops forever. If it were a normal thread, the program would never end. As a daemon, it is shut down when main finishes.

    Cheat sheet
    

    ThingOne lineClassic mistake
    

    start()Creates a new thread that runs run()Calling run() instead: no new thread
    

    synchronizedOne thread inside at a timeTouching shared data outside it
    

    wait()Put the lock down and napCalling it outside synchronized; not re-checking after waking
    

    notify()Wake one napping threadForgetting it, so the napper never wakes
    

    Thread.sleep()Nap but keep the lockUsing it inside synchronized: everyone else is stuck
    

    setDaemon(true)Java won't wait for this thread to exitCalling it after start()
