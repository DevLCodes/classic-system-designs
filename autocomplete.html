Search Autocomplete

Design the suggestion box under a search bar: as the user types, show the 10 most likely completions of what they have typed so far. Plan for 500 million daily users, 5 billion searches a day, and an answer fast enough to keep up with typing. Breaking news should show up within minutes, and nothing offensive or private should ever be suggested.

Requirements

  • Clarify
  • Non-functional requirements

Autocomplete is a read problem with a strict clock. Each answer is tiny, almost all of them can be computed ahead of time, and the user is already typing the next letter.

QuestionAssumptionWhy it matters
FeaturesTop 10 completions of the typed prefix, ranked by popularity; trending terms; a few of your own past searchesShared answers can be cached; personal ones can't
Users500M a day, 10 searches each5B searches a day
Requests~6 suggestion calls per searchOne per pause in typing, not one per key
Latencyunder ~100 ms end to endA typist presses a key every 200–300 ms; slower answers arrive for a prefix the user has already left
Freshnessdaily for the long tail; minutes for spikesA batch job plus a streaming overlay
SafetyNo hateful, sexual, violent or defamatory suggestions; no personal dataFilters at build time and at serve time, plus a fast kill switch
LanguagesPer locale (en-IN, hi-IN, …)Separate lists; locale is part of the cache key

Out of scope: the search results page itself, spelling correction beyond simple normalization, and ads in the suggestion box.

Estimates

  • Back of the envelope
  • Numbers
  • Requests: 5B searches × ~6 calls each = 30B a day ≈ 350k a second, about 700k at the evening peak. Without debouncing (one call per key, ~20 keys per search) it would be over 1M a second.
  • What to index: billions of distinct queries a day, but most are typed once. Keep queries seen by enough different people, roughly the top 100M. At ~20 characters each that is ~2 GB of text.
  • Prefixes: 100M queries × 20 characters is 2B prefixes before sharing; shared starts ("how to …") cut that to roughly 1B. Each stores a key and the ids of its top 10 queries, ~60 bytes, so one full copy is ~60 GB. That fits in RAM across 4 shards of ~16 GB.
  • After caching: if browsers and the CDN answer ~80% (the lab shows where that comes from), the origin sees ~70k a second on average. A server reading from RAM handles tens of thousands of lookups a second, so a few replicas per shard per region is plenty.

API

  • Interface
GET /api/suggest?q=how%20t&loc=en-IN&v=812        (public, cacheable)
→ 200  Cache-Control: public, max-age=3600
  { prefix: "how t", suggestions: ["how to tie a tie", "how to train your dragon", …] }

GET /api/suggest/personal?q=how%20t                  (private, signed in, optional)
→ 200  Cache-Control: private, no-store
  { recent: ["how to tie a saree"] }

POST /api/search  { q: "how to tie a tie", picked_from: "suggestion", pos: 1 }   (logged)

The shared call takes no cookies, so the same prefix and locale give the same bytes for everyone, which is what lets a CDN cache it. v is the index version: a new snapshot changes the URL, so the old cached answers age out on their own. The personal call is separate and never cached at the edge.

Architecture

  • Whole system

The trie and top-k

  • Deep dive 1
  • Indexes
  • Sharding

A trie is a tree of characters: every query is a path from the root, and every prefix is a node. The trick that makes it fast enough is to store each node's answer on the node.

  • Naive version: walk to the prefix node, then visit every query below it and sort by count. For "a" that is tens of millions of queries per keystroke. Far too slow.
  • Top-k per node: precompute each node's 10 best completions when the trie is built. A lookup is then one step per character plus one read: microseconds in RAM. The price is memory (10 ids at every node) and that the trie can't cheaply change in place, which is fine because it is rebuilt offline.
  • Store ids, not strings: each list holds 4-byte query ids into a shared string table, so "how to tie a tie" is stored once, not at each of its 16 prefixes.
  • Flatten it for serving: once every node has its answer, you no longer need the tree at serve time. A plain key-value map prefix → [ids] gives the same answers, can live in any in-memory store, and can be sharded by a hash of the prefix. The trie is how you build the answers; the map is how you serve them.
  • Sharding: sharding a real trie by first letter is lopsided ("s" has far more queries than "x"). Hashing the flat map's keys spreads them evenly. The hottest keys are the 1–2 letter prefixes, and those almost always hit a cache before they reach a shard.
  • Long prefixes: past ~20 characters, stop storing nodes. Few people type that far without picking, and the rare request can be answered from the length-20 node, filtered on the fly.

Building it offline

  • Deep dive 2
  • Message queues and streams
  • Hot partitions

Popularity is counted from what people actually searched, not from keystrokes. A daily job turns yesterday's logs into a new, immutable index.

  1. Collect: every submitted search (not every keystroke) goes to Kafka with locale, coarse country and time. A copy lands in object storage for reprocessing.
  2. Normalize: lowercase, trim, collapse spaces, Unicode-normalize (so "café" typed two ways is one query), and strip obvious junk like URLs and long digit strings.
  3. Count with decay: score = Σ daily count × 0.5age in days ÷ 7. A one-week half-life lets last month's hits fade without forgetting evergreen queries like "weather".
  4. Drop the rare: keep a query only if enough different users searched it (say 20+ in the window). This cuts the index from billions of queries to ~100M and keeps one person's typed phone number or address out of everyone's suggestions.
  5. Filter: remove anything matching the blocklist (see filtering).
  6. Build top-k bottom-up: each node's list is the best 10 among its own query (if it is one) and its children's lists. Merging small sorted lists from the leaves up visits every node once, so the whole build is a few hours of batch compute, sharded by prefix.
  7. Ship: write the result as a versioned snapshot (v812) to object storage. Serving replicas load it next to the old one, check it with a set of golden prefixes, then switch over (blue/green). Rolling back is pointing at v811 again.

The whole index is rebuilt rather than patched. That makes it easy to reason about: every replica serves exactly one version, and a bad build is fixed by loading the previous file.

Edge and browser caching

  • Deep dive 3
  • Caching
  • CDNs

The shared answer for a prefix is the same for everyone in a locale, so it should be served as close to the user as possible. The fastest request is the one the browser never sends.

In the browser

  • Debounce: wait ~100–150 ms after the last key before asking. Fast typists skip the middle prefixes entirely, which cuts requests by about two thirds.
  • Remember answers: keep the last few hundred prefix answers in memory. Backspacing from "how to f" to "how to " costs nothing, and the HTTP cache keeps them across page loads for the max-age.
  • Drop stale replies: cancel the in-flight request when a new one starts, or tag each with a sequence number and ignore answers for a prefix the user has already left. Otherwise a slow reply for "ho" can overwrite the list for "how t".
  • Filter locally: if the list for "how t" has fewer than 10 entries, it already contains every completion of "how to", so the browser can filter it instead of asking again.

At the edge

  • Cache key: prefix + locale + index version, nothing else. No cookies, no user id, so one cached copy serves millions of people.
  • TTL by heat: an hour for most prefixes; 60 seconds for prefixes that currently have a trending entry, so a spike shows up quickly and falls away quickly.
  • Short prefixes are gold: there are only ~36 one-character and ~1,000 two-character prefixes, and they carry a big share of traffic. Every edge location holds them all. Longer prefixes are more numerous and less popular each, so the cache holds only the most popular ones. The lab shows the trade-off.
  • Removal: when a term must disappear (a court order, a bad build), purge its prefixes from the CDN by key, or bump the index version so every cached answer is bypassed at once.

Edge cache size

Rough model: requests by prefix length run from 10% for 1 character, peaking at 13% for 3–4 characters, down to 3% for 12; the number of distinct prefixes grows from 36 (1 character) to 450M (12 characters); popularity within each length follows a Zipf curve. The browser cache answers the ~20% of requests that repeat a prefix that browser already fetched. Illustrative, not measured.

Trending terms

  • Deep dive 4
  • Streams
  • Live comments

An earthquake hits at 2 pm. By 2:05 a million people are typing "earthq…", and last night's index has never heard of today's earthquake. A small streaming path fills the gap until the next build.

  • Detect: a stream job (Flink, Kafka Streams) counts each normalized query per 5-minute window and compares it with the same query's usual rate. "40× normal and at least 2,000 searches" is trending; "always popular" is not.
  • Publish: write the trending query under each of its prefixes in Redis, with a score and a 2-hour TTL. Only a few thousand queries trend at once, so this store is megabytes, not gigabytes.
  • Merge at serve time: the suggestion service reads the base top 10 and the trending list for the prefix in parallel, puts at most one or two trending items near the top, and removes duplicates.
  • Hot keys: a trending prefix is exactly the key everyone asks for. The short edge TTL means each edge location asks the origin about once a minute for it, no matter how many users type it.
  • Guard it: trending terms skip the 24-hour vetting of the daily build, so they pass the same blocklist at serve time, need a minimum number of distinct users, and are watched more closely. Coordinated campaigns to push a term are the main abuse.

Personalization and filtering

  • Deep dive 5
  • Gateways

Personal, without breaking the cache

  • Keep shared and personal apart: the shared list comes from the edge cache; your own past searches come from a separate private call or from storage on the device. The browser merges them: up to two of your matching recent searches first, then the shared list without duplicates.
  • Cheap context in the key: locale and coarse country can go in the cache key ("cricket score" means different matches in India and Australia). Anything finer, like city or user, would split the cache into millions of tiny pieces with no hits.
  • Re-rank lightly: a signed-in user's list can be re-ordered by a small model on the service (interests, recent topics), but only within the top 20 candidates from the shared list, so the expensive part stays shared.
  • Respect the off switch: history is deletable and can be turned off; incognito sends only the shared call.

Filtering

  • At build time: drop queries matching lists for hate, sexual content, violence and self-harm, plus "person's name + negative claim" patterns that could defame someone. A classifier catches variants the lists miss.
  • At serve time: the suggestion service checks every outgoing suggestion against an in-memory blocklist pushed to all replicas within minutes. This is the kill switch for things found after the build.
  • Privacy: the distinct-user threshold keeps one person's unusual search (their address, a medical question) from ever becoming a suggestion for others.
  • Removal flow: add to the blocklist, purge or version-bump the edge, and confirm with a probe that the term is gone everywhere, which meets the 15-minute target.

v2 ideas: typo-tolerant matching ("hwo to" → "how to"), completions from the middle of a query ("tie" matching "how to tie a tie"), prefetching the likely next prefix's answer, and per-vertical lists (shopping, maps, videos).

"Every answer is precomputed. A daily job counts submitted searches with a one-week decay, drops rare and blocked queries, and builds a trie where each node stores its top 10 completions as ids. That is flattened into a prefix-to-list map, hash-sharded across a few in-memory replicas and loaded blue/green from a versioned snapshot. The shared answer depends only on prefix and locale, so the browser debounces and caches, and the CDN caches with an hour TTL; together they absorb over 80% of requests. A streaming job spots spikes in 5-minute windows and writes them to a small Redis overlay that the service merges in, with a short edge TTL for those prefixes. Personal history is merged in the browser so it never splits the cache, and every suggestion passes a serve-time blocklist that we can update in minutes."
