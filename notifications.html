Classic system design walkthrough

Notification System

Design the notification platform for a large consumer app. Every team sends push, SMS, email and in-app messages through one service. Users choose what they get and when. A login code must arrive in seconds, even while a marketing campaign to 50 million people is going out. Plan for 300 million users and about 2 billion notifications a day.

Requirements

  • Clarify
  • Non-functional requirements

A notification system is a router with opinions. Other services say "the order was delivered". This service decides whether the user wants to hear it, on which channel, at what time, and makes sure it gets there exactly once as far as the user can tell.

QuestionAssumptionWhy it matters
ChannelsPush (iOS, Android, web), SMS, email, in-app inboxEach channel has its own provider, limits, cost and failure modes
Users300M, ~1.5 devices eachDevice tokens and preferences to store and look up
Volume~2B a day~23k a second on average
KindsTransactional (OTP, order updates, fraud alerts) and marketing campaignsDifferent urgency, different rules, must not share one queue
Campaignsup to 50M users in ~30 minBursts of ~28k a second on top of normal traffic
LatencyOTP handed to provider in < 2 s; order updates < 10 sCritical traffic needs its own lane
User controlOpt out per category and channel; quiet hours in their time zone; frequency capsPreferences checked on every send
CorrectnessNo duplicates the user can see; no marketing to opted-out usersDedupe, idempotency keys, a preference check that fails closed

Out of scope: choosing campaign audiences (assume a segment service hands us a list of user ids), and what the messages say. Chat messages have their own delivery path: Chat service.

Watch the guardrails as closely as the speed. A system that sends faster but makes people turn notifications off has failed.

Estimates

  • Back of the envelope
  • Numbers
  • Average: 2B a day ÷ 86,400 s ≈ 23k a second. Evenings and campaigns push it to 4–5×, so plan for about 100k a second at the send stage.
  • Channel mix: push 1.5B, in-app 300M, email 180M, SMS 20M a day. SMS is about 1% of messages but most of the bill, because providers charge per message (from a fraction of a cent to several cents, depending on the country).
  • Campaign: 50M users in 30 minutes = 50M ÷ 1,800 s ≈ 28k a second for half an hour, on top of everything else.
  • Storage: device tokens 300M × 1.5 × ~250 B ≈ 110 GB; preferences 300M × ~200 B ≈ 60 GB. Both fit in a cached key-value store. The delivery log is 2B × ~500 B ≈ 1 TB a day; 30 days hot is ~30 TB before replication.

API

  • Interface
POST /v1/notifications            Idempotency-Key: order-981-delivered
  { user_id, type: "order_delivered", priority: "critical|high|normal|bulk",
    data: { order_id: 981, eta: "now" }, channels?: ["push","inapp"],
    expires_at: "+30m" }
→ 202 { notification_id }

POST /v1/campaigns
  { segment_id, template_id, send_at, max_rate_per_s: 20000,
    respect_quiet_hours: true }
→ 202 { campaign_id }

PUT  /v1/users/{id}/preferences
  { categories: { marketing: { push: false, email: true } },
    quiet_hours: { start: "22:00", end: "08:00", tz: "Asia/Kolkata" } }

POST /v1/devices    { user_id, platform: "ios|android|web", token }
GET  /v1/notifications/{id}   → { status, attempts: [...] }

POST /hooks/{provider}/receipts   (delivery reports from providers)

Callers send an event type and data, not finished text. That way the platform owns templates, language, channel choice and user rules, and a team can't bypass someone's opt-out by accident. The call returns 202 straight away: sending is always asynchronous.

Architecture

  • Whole system
  1. API: checks the caller is allowed to send this type, stores the idempotency key, writes the request to Kafka and returns 202.
  2. Planner: loads the user's preferences and devices (cached), drops channels they opted out of, moves non-urgent messages out of quiet hours, checks frequency caps and dedupe, renders the template, and emits one message per channel.
  3. Queues: one Kafka topic per priority, plus a scheduled store for messages that wait until morning.
  4. Workers: one pool per channel. They batch where the provider allows it, apply per-provider rate limits and retry with backoff.
  5. Receipts: providers call back with "delivered", "bounced" or "invalid token". A receipts service maps the provider's message id to ours and updates the log.

Channels and providers

  • Deep dive 1
  • Polling vs push

You don't deliver to phones yourself. You hand each message to the one company that can reach that device or inbox, and each has its own rules.

ChannelWho delivers itWhat you must handle
PushAPNs for Apple devices, FCM for Android and webDevice tokens that change and expire; small payloads (about 4 KB); remove a token when the provider says it is no longer registered; collapse keys so ten updates show as one
SMSAggregators that connect to mobile carriersCost per message; sender ids and registered templates (India's DLT rules, US 10DLC); 160-character segments; delivery reports that arrive minutes later
EmailAn email service (SES, SendGrid and others) or your own mail serversSPF, DKIM and DMARC so mail isn't marked spam; warming up new IPs slowly; bounces and complaints; one-click unsubscribe headers
In-appYou: an inbox table plus a live push if the app is openRead and unread state; it is the only channel you fully control, so it is also the fallback record of everything sent

Push is free and fast, so it is the default. SMS is reserved for codes and critical alerts, where it is the most reliable way to reach someone without the app. Email suits receipts and long content.

Push has no second provider. APNs is the only way to reach an iPhone. If APNs is slow, the only options are to wait or to fall back to a different channel for messages that really matter.

Preferences, quiet hours and templates

  • Deep dive 2
  • Caching

Every send passes the same checks, in the same order. Getting this wrong is how companies end up texting people at 3 am.

  1. Must-send types skip the opt-outs. Login codes, security alerts and legal notices go out whatever the user chose for marketing. Mark these types in the type registry, not in the caller's request.
  2. Category and channel opt-outs. Preferences are a small document per user: {marketing: {push: off, email: on}, order_updates: {push: on}}. They are read on every send, so they sit in a key-value store with a cache in front. If the preference lookup fails, marketing is dropped, not sent.
  3. Quiet hours in the user's time zone. A non-urgent message that lands at 23:10 for a user with 22:00–08:00 quiet hours goes into a scheduled store, keyed by send time, and a scheduler moves it back into the queue at 08:00 their time. Campaigns respect time zones the same way: "9 am local" is really 24 separate sends.
  4. Frequency caps. At most, say, 3 marketing pushes a day per user. A counter per user per day in Redis, incremented when a message is sent.
  5. Expiry. "Your driver is 2 minutes away" is useless after 10 minutes, and a login code after 5. Each message carries expires_at, and workers drop it instead of sending late.

Templates

Templates live in a versioned store: one template per type, per channel, per language. order_delivered.push.hi-IN v4 might be "आपका ऑर्डर पहुँच गया". The planner renders it with the event's data at send time, so fixing a typo needs no change in any calling service. SMS templates often must be registered with carriers first, so a new SMS template is a release, not a quick edit.

Priority queues

  • Deep dive 3
  • Message queues

If a 50-million-user campaign and a login code share one queue, the login code waits behind 50 million messages. Separate lanes fix that.

LaneExamplesRules
CriticalLogin codes, fraud alerts, password resetsOwn topic and workers; a share of every provider's limit reserved for it; expire in minutes
High / normalOrder and delivery updates, replies, remindersNormal workers; seconds of delay is fine
BulkCampaigns, digests, newslettersPaced by a campaign rate limit; uses whatever capacity is left; paused first when providers struggle

Strict priority (always drain critical first) can starve bulk forever on a busy day. Use separate consumer pools with fixed shares instead, and let bulk borrow idle critical capacity but never the other way round.

A campaign doesn't put 50M messages on Kafka at once. A campaign runner pages through the segment and writes, say, 20k messages a second, so a cancel button can stop it within seconds and nothing goes out to users who opted out in the meantime.

Dedupe and rate limits

  • Deep dive 4
  • Rate limiting
  • Distributed rate limiter

Queues and retries deliver at least once. The user should still see each notification once.

  • Idempotency at the API: the caller's Idempotency-Key is stored for 24 hours. A retried call returns the same notification_id and sends nothing new.
  • Dedupe before sending: a worker runs SET sent:{notification_id}:{channel} 1 NX EX 86400 in Redis before calling the provider. If the key already exists, another worker (or an earlier attempt) already sent it.
  • Collapse similar messages: five "new comment" events in a minute become one "5 new comments" push. Push providers also support a collapse key, so a newer message replaces an older one still waiting on the device.

Rate limits work at three levels:

LimitProtectsHow
Per callerEveryone else, from one buggy service sending in a loopToken bucket per calling service and type at the API
Per userThe user's patienceFrequency caps per category per day
Per providerThe provider contract; going over gets you throttled or blockedShared token bucket in Redis per provider account, split across workers

Primary outage

Illustrative limits: SMS primary 2,000/s and backup 800/s; email primary 5,000/s and backup 2,000/s; push 40,000/s through APNs and FCM with no backup. The outage starts at minute 5. Real limits are set in each provider contract.

Retries and provider failover

  • Deep dive 5
  • Observability
  • Payments: the unknown state

Providers fail all the time, in small ways and big ones. The worker's job is to tell a temporary failure from a permanent one, and to stop hammering a provider that is down.

ResponseMeaningAction
Timeout, 5xxTemporary, and the message may or may not have gone outRetry with exponential backoff and jitter (1 s, 2 s, 4 s…), keep the same idempotency key
429, throttledYou went over the limitSlow the shared token bucket for that provider, then retry
Invalid number, unregistered token, hard bouncePermanentDon't retry. Delete the token or mark the address bad so you stop paying for it
Too many failures in a rowThe provider is downCircuit breaker opens: stop sending to it, fail over, and test it with one request every 30 s (half-open)
  • Retry budget: at most, say, 5 attempts or until expires_at. Then the message goes to a dead-letter queue with its last error, so someone can look at it and nothing disappears silently.
  • Failover by channel: SMS and email have backup providers (usually pricier or slower, so they are not used all the time). Push can't fail over to another provider. For critical messages the fallback is another channel: if the app hasn't confirmed a security alert within a minute, send an SMS.
  • Move back slowly: when the primary recovers, shift traffic back in steps (10%, 50%, 100%) so you don't knock it over again.

Delivery tracking

  • Deep dive 6
  • Event streams

"Did the user get it?" is the first question support will ask. Each message has a status, and every attempt is logged.

ACCEPTED → SUPPRESSED (opted out, capped, duplicate)
         → SCHEDULED (quiet hours) → QUEUED → SENT (provider accepted)
         → DELIVERED (receipt) → OPENED / CLICKED
         ↘ FAILED (permanent) · EXPIRED (too late) · DEAD_LETTERED
  • Provider receipts are asynchronous. SMS delivery reports and email bounces arrive by webhook seconds to hours later. Store the provider's message id with each attempt so a receipt can find its notification.
  • Push confirms less than you'd hope. APNs and FCM confirm they accepted the message, not that the phone showed it. For a true "received", the app reports it back when the notification arrives, and again when it is opened.
  • Email opens are fuzzy. Open tracking uses a tiny image, and some mail apps load every image in advance. Trust clicks and bounces more than opens.
  • Events, not just rows: every status change is also an event on Kafka, feeding campaign dashboards, A/B results and the feedback loop that removes bad tokens and addresses.

  • Wrap-up

v2 ideas: pick the best time to send for each user from when they usually open, pick the channel each user responds to, a digest that batches low-priority updates into one daily message, and least-cost routing across SMS providers by country.

"Services send an event type and data to one API, which returns 202 and records the idempotency key. A planner checks the user's preferences, quiet hours and caps, renders the template, and writes one message per channel onto a Kafka topic for its priority. Critical messages like login codes have their own topic, workers and a reserved share of each provider's limit, so a 50-million-user campaign can't delay them. Channel workers send through a router with per-provider token buckets and circuit breakers; temporary errors retry with backoff, permanent ones clean up the token or address, and SMS and email fail over to a backup provider. Receipts come back by webhook into a Cassandra log, so we can answer 'did they get it?' for every message."
