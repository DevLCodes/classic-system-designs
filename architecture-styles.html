Monoliths, microservices and hexagonal architecture

How to cut a system into pieces: one deployable app, one app with strict modules inside, or many small services that talk over the network. And how to keep business rules apart from databases and frameworks, whichever you pick.

Three ways to cut a system

The question is not "monolith or microservices". It is where the boundaries go, and whether crossing one is a function call or a network call.

MonolithModular monolithMicroservices
Deploy unitOneOneOne per service
Call between partsFunction call, about 1 µs or lessFunction call through a module APINetwork call, about 0.5 to 5 ms in one data centre
DataShared tables, joins everywhereOne DB, each module owns its tablesEach service owns its database
TransactionsOne ACID transactionOne ACID transactionSagas, outbox, idempotency
ScaleWhole app togetherWhole app togetherEach service on its own
TeamsWorks up to a few teamsMany teams, one release trainTeams ship on their own schedule
Main riskTurns into a tangle nobody can changeWalls erode if nothing enforces themNetwork, ops and data consistency cost

A monolith is not a bad word. One codebase, one deploy, one database is the fastest way to build and the easiest to debug. It goes wrong when every part reaches into every other part, so a change anywhere can break anything.

A modular monolith keeps one deploy but splits the code into modules with clear public interfaces. Orders may call payments.charge(), but may not read the payments tables. A build check enforces it. This gives most of the design benefit of services with none of the network cost.

Microservices make each module its own process with its own database, deployed and scaled on its own. You gain independent releases and independent scaling. You pay with network calls, partial failures, data spread across stores, and a lot more to operate.

Ports and adapters

Hexagonal architecture (Alistair Cockburn, 2005) is about the inside of one app or one service. Keep the business rules in a core that knows nothing about HTTP, SQL or a vendor SDK. The core declares ports: interfaces for what it needs and what it offers. Adapters plug real technology into those ports.

The rule that makes it work is the dependency direction: source code dependencies point inward. The core defines OrderRepository; the Postgres adapter implements it. The core never imports the database driver.

  • Tests get fast. Run the core against in-memory fakes. Thousands of business-rule tests finish in seconds with no database or network.
  • Vendors stay replaceable. A payment provider change touches one adapter, not every place that charges a card.
  • It makes a later split cheaper. If the Orders core only talks to Payments through a port, turning that port into a network client is a local change.

Clean architecture and onion architecture are close cousins with the same inward rule. The cost is more interfaces and mapping code. For a small CRUD app with almost no rules, that can be more ceremony than it is worth.

Boundaries and data ownership

Most of the value, and most of the pain, of splitting comes from where you draw the lines.

Cut by business capability

Good boundaries follow the business: orders, payments, catalog, shipping. Domain-driven design calls each one a bounded context: an area where words have one meaning. "Product" in the catalog has photos and descriptions; in the warehouse it has a bin location and a weight. Two contexts, two models, and that is fine.

Bad boundaries follow technical layers: a "database service", a "validation service", an "email-templates service". Every feature then has to change all of them, so they must deploy together anyway.

A quick test: can one team ship a typical feature by changing one service? If most features touch three services, the boundaries are wrong, and you have the costs of microservices without the independence.

One owner per piece of data

Each service owns its tables. Nobody else reads or writes them directly. Other services get the data in one of three ways:

HowExampleTrade-off
Ask the owner (API call)Checkout calls Users for the shipping addressAlways fresh; adds latency and a runtime dependency
Listen to its eventsSearch keeps its own copy of products from product-updated eventsFast local reads; the copy is a little stale
Change data captureA connector streams the owner's database log into KafkaNo code change in the owner; you depend on its table layout

A shared database between services looks like a shortcut. It is the most common way to end up with a distributed monolith: separate deploys that still break each other on every schema change.

Conway's law

Melvin Conway observed in 1968 that systems end up shaped like the teams that build them. Use it on purpose: one team should own one service end to end. If two teams share a service, they will fight over its release schedule. If one team owns ten tiny services, it pays the overhead ten times.

Sync and async calls

Sync (REST, gRPC)Async (queue, Kafka topic)
Caller getsAn answer nowAn acknowledgement; the result comes later
If the callee is downThe caller fails or waitsMessages wait in the broker
LatencyAdds up along the chainOff the user's path
ConsistencyEasier to reason aboutEventual; duplicates and reordering happen
Use forReads the user waits for; checks that must pass first (stock, fraud)Side effects: email, search indexing, analytics, fan-out

Rules for sync calls

  • Set a timeout on every call. Shorter than the caller's own deadline, and pass the remaining deadline downstream so deep calls give up when the user already has.
  • Retry only idempotent calls, with backoff and jitter, and with a retry budget so retries cannot multiply load during an outage. See the retry storm lab in API gateways.
  • Use a circuit breaker so a dead dependency fails fast instead of tying up threads.
  • Fan out in parallel when calls do not depend on each other, and degrade gracefully: a product page without recommendations is better than no page.

Rules for async calls

  • Assume at-least-once delivery: make consumers idempotent with a dedupe key.
  • Write the event in the same transaction as the state change with a transactional outbox, or you will one day update the row and lose the event.
  • A workflow across services (reserve stock, charge card, ship) is a saga: a series of local steps, each with a compensating step to undo it. See queues and consistency.

Try it: a request that calls N services

One user request needs data from N downstream services. Each call usually takes 10 ms, but 1 in 100 calls is slow (its p99). Each service is up with the availability you pick. Compare calling them one after another with calling them all at once.

Calls
Each service up

Each call's time is drawn from a log-normal curve with a 10 ms median and the p99 you set; 20,000 simulated requests per setting, with a fixed seed so results repeat. Failures assume services fail independently and no retries. Illustrative.

Two lessons fall out. First, sequential chains add up: five calls with a 10 ms median give a median request of about 60 ms and a p99 of about 130 ms. Second, parallel calls fix the average but not the tail: the request waits for the slowest call, so the more calls you make, the more likely one is slow. At 10 calls, about 1 request in 10 hits at least one call's p99 (1 − 0.9910 ≈ 9.6%). At 100 calls it is 63%. This is the "tail at scale" effect Google wrote about in 2013.

chance a request fails = 1 − aN
chance it meets a slow call = 1 − 0.99N

Fixes: call fewer services on the hot path (combine data in a read model), cache, give each call a tight timeout with a fallback, and for idempotent reads send a hedged request to a second replica if the first has not answered by about the p95.

When splitting pays off

Start with a well-structured monolith, ideally modular with hexagonal cores. Split a piece out when a specific pain shows up, not because the system "should" be microservices.

SignalWhy a split helps
Many teams block each other on one release trainIndependent deploys let each team ship on its own schedule
One part needs very different scaleScale the image resizer to 200 machines without scaling the admin pages
One part needs different hardware or runtimeGPU inference, a JVM search engine, a Go websocket gateway
A failure in one part takes everything downA process boundary contains a memory leak or a crash loop
Strict compliance scopeKeep card data in a small PCI-scoped service, away from the rest

Reasons that do not justify a split on their own: "the code is messy" (fix the modules first; a messy monolith becomes messy services), "we might need to scale" (one well-tuned database and a few app servers go a very long way, see numbers to know), and "everyone else does it".

What a split costs

  • Network calls: latency, timeouts, retries and partial failure on every boundary.
  • No cross-service transactions: sagas, outboxes and reconciliation instead of one COMMIT.
  • Operations: a deploy pipeline, dashboards, alerts, on-call and capacity plan per service.
  • Debugging: you need distributed tracing to see one request across ten processes.
  • Versioning: APIs and event schemas must stay backward compatible while callers upgrade.

How to split: the strangler fig

Do not rewrite. Put a routing layer (often the API gateway) in front of the monolith. Build the new service for one capability, send its routes to it, and keep the rest going to the monolith. Move the data last: dual-write or stream it with change data capture, compare, then cut over. Repeat. The old system shrinks until it can be retired. Martin Fowler named the pattern after a vine that grows around a tree.

How it goes wrong

The distributed monolith

Services that must be deployed together, share a database, or call each other in long chains. You pay all the costs of microservices and get none of the independence. Fix the boundaries, or merge the services back.

Chatty services

A page that makes 40 calls to render, or a loop that calls another service once per item. Batch the calls (getUsers(ids), not 50 × getUser(id)), or keep a local read model fed by events.

Cascading failure

One slow dependency fills every caller's thread pool, and the callers stop answering their own callers. Timeouts, circuit breakers, bulkheads (a separate pool per dependency) and load shedding stop the spread.

Breaking changes

A service renames a field and three consumers crash. Only add fields, never remove or rename without a deprecation window, and test against consumers' expectations with contract tests.

Too many, too small

Fifty services for a ten-person team means each engineer owns five pipelines and five on-call rotations. A service should be big enough that one team can own it end to end and small enough that it can.

Leaking frameworks into the core

Inside a service, the domain code imports ORM entities, HTTP request objects and a vendor SDK. Now a framework upgrade touches business rules, and tests need a database. Ports and adapters fix this.

Saying it in an interview

"I'd start with a modular monolith: one deployable with orders, payments and catalog as separate modules, each owning its tables, each with a hexagonal core so business rules don't depend on Postgres or the payment SDK. I'd split a module into its own service only when there's a concrete reason: a team needs to deploy independently, it needs very different scale, or it should be isolated for compliance, like card data. Across services, the user-facing path stays synchronous and short, with timeouts and parallel fan-out; side effects like email, search indexing and analytics go through Kafka with an outbox and idempotent consumers. I'd watch the call depth, because with five sequential 10 ms calls the p99 is already well over 100 ms, and every extra 99.9% dependency adds about 0.1% failed requests."

Public stories worth knowing: Shopify runs one of the largest Rails monoliths as a modular monolith and built Packwerk to enforce its boundaries. Segment wrote "Goodbye Microservices" (2018) after merging more than 140 near-identical destination services back into one. In 2023 a Prime Video team moved an audio and video quality-monitoring tool from distributed serverless components into a single process and reported over 90% lower infrastructure cost. Netflix and Amazon, on the other side, run thousands of services because they have thousands of engineers who need to ship independently.
