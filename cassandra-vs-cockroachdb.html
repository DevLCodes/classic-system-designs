Cassandra vs CockroachDB

Two distributed databases that both scale by adding nodes and survive node loss, built on opposite bets. Cassandra is leaderless and favours always-on writes; CockroachDB runs Raft per range and gives you serializable SQL. Knowing why they differ teaches most of distributed storage.

How Cassandra works

  • Ring and tokens. The partition key is hashed (Murmur3) to a token. Each node owns several token ranges (virtual nodes), and the next RF nodes clockwise hold the replicas; see consistent hashing. Nodes learn about each other by gossip; there is no master.
  • Coordinator. The client talks to any node, which forwards the request to the replicas and waits for as many as the consistency level asks: ONE, QUORUM (2 of 3), ALL, or LOCAL_QUORUM to stay inside one datacenter.
  • Tunable consistency. If reads plus writes overlap (R + W > RF, such as QUORUM and QUORUM) a read sees the latest acknowledged write. ONE/ONE is faster and more available but can return stale data. See quorums.
  • Convergence. Replicas that missed writes catch up through hinted handoff, read repair and Merkle-tree repair. Concurrent writes to the same cell resolve by last write wins on timestamp.
  • Query-first modelling. No joins and limited secondary indexes, so you design one table per query, partitioned by what you look up and clustered by how you sort. Data is duplicated across tables on purpose. Keep partitions bounded (a common guideline is under about 100 MB).
  • Lightweight transactions (IF NOT EXISTS) use Paxos for compare-and-set on one partition, at about four round trips. Use them sparingly.

How CockroachDB works

  • One sorted key space. Every table and index row becomes a key like /table/index/primary-key. The key space is cut into ranges, 512 MB by default (64 MB in older versions). Ranges split when they grow or get hot and are rebalanced across nodes.
  • Raft per range. Each range's replicas (3 by default, 5 for important data) form a Raft group. A write commits once a majority has it in their log. A cluster has thousands of small Raft groups, so leadership and load spread across all nodes.
  • Leaseholder. One replica holds a lease and serves reads without a round of consensus, since it knows every committed write. It is usually also the Raft leader.
  • Transactions. Writes are laid down as intents (provisional values) plus a transaction record; commit flips the record and intents resolve afterwards. Keys are versioned (MVCC) with hybrid logical clock timestamps, so reads see a consistent snapshot. Conflicting transactions wait or restart; clients should retry on serialization errors.
  • Clocks. Nodes need loosely synchronized clocks (a 500 ms maximum offset by default). A read that sees a value with a timestamp inside its uncertainty window may restart. A node whose clock drifts too far shuts itself down rather than risk wrong answers.
  • Multi-region. Tables can be pinned to a home region, so reads and writes in that region are fast, or replicated globally for fast reads everywhere at the cost of slower writes.

Inside a write

Both store data on disk in an LSM tree: Cassandra in its own SSTable engine, CockroachDB in Pebble (a RocksDB-style engine). The difference is what happens before the disk.

StepCassandra (QUORUM, RF 3)CockroachDB (RF 3)
1Client sends to any node; it becomes coordinatorGateway node finds the range's leaseholder
2Coordinator sends the write to all 3 replicas in parallelLeaseholder checks for conflicts, writes an intent, proposes it to Raft
3Each replica appends to its commit log and memtableFollowers append to their Raft log
4Success after 2 acks; the third catches up laterCommitted after a majority (2 of 3); applied to the state machine
5Memtables flush to immutable SSTables; compaction merges themCommit flips the transaction record; intents become values
CostOne round trip to the replicas, no reads before writesA consensus round trip per range written, plus transaction bookkeeping

Cassandra writes are blind (no read first) and sequential on disk, which is why a node can take tens of thousands of writes a second. Reads pay instead: they may merge a memtable and several SSTables (bloom filters skip most), so the compaction strategy matters, such as size-tiered for writes, leveled for reads, time-window for time series.

Rough model: in one region a replica round trip is about 1 ms; across three regions each replica sits in a different region about 70 ms away. CockroachDB's leaseholder is in the client's region and the replicas that go down are remote ones; losing the leaseholder itself adds a few seconds while the lease moves.

Choosing

Pick Cassandra whenPick CockroachDB when
Writes dominate and must never be refused: events, metrics, messages, IoTYou need transactions across rows and tables: orders, payments, inventory, accounts
Access patterns are known and simple (by key, by key and time range)Queries change over time and need joins and secondary indexes
Stale reads for a moment are acceptable, or you can pay QUORUM where they aren'tReads must always reflect committed writes
You want the lowest write latency, including across regions with LOCAL_QUORUMYou can afford consensus latency per write in exchange for correctness

Other options sit near each: ScyllaDB and DynamoDB are Cassandra-like; Spanner, YugabyteDB and TiDB are CockroachDB-like. And if one Postgres with replicas fits your data for the next few years, that is still the simplest answer; see Databases.

Failure modes

Cassandra: lost updates and zombie data

Last write wins means two concurrent updates silently drop one, and clock skew between clients can make an older write win. Deletes leave tombstones; too many slow reads, and a replica that misses repair for longer than the grace period can bring deleted data back.

Cassandra: hot and huge partitions

A partition key with low cardinality (a country, today's date) puts a huge share of traffic and data on three nodes. Add a bucket to the key, such as (sensor_id, day).

CockroachDB: contention and retries

Many transactions writing the same rows (a global counter, one popular product's stock) queue and restart. Spread hot keys, keep transactions short, and always retry serialization errors in the client.

CockroachDB: sequential keys

Auto-incrementing primary keys send all inserts to the last range, so one node takes every write. Use UUIDs or hash-sharded indexes.

Both: running out of headroom

Compaction (Cassandra) and rebalancing (both) need spare disk and I/O. Keep disks well under full, often at most about 50–70% for Cassandra with size-tiered compaction.

Saying it in an interview

"For the message history I'd use Cassandra: writes dominate, the access pattern is fixed (messages by conversation, newest first), so the partition key is conversation id plus a time bucket and the clustering key is the message time. I'd write and read at LOCAL_QUORUM, so each region is consistent and fast and stays up when a node dies. For balances and orders I'd use CockroachDB or Spanner: those need multi-row transactions and must never show a stale balance, and I accept a consensus round trip per write. The two are connected by events through a queue, not by joins."
