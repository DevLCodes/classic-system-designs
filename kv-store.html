Distributed Key-Value Store

Design a key-value store like Amazon's Dynamo or Cassandra: put(key, value) and get(key), spread over many machines, that keeps taking writes when machines and links fail. Plan for 10 billion keys of about 1 KB, a million operations a second at peak, and reads and writes under 10 ms at p99.

Requirements

  • Clarify
  • Non-functional requirements

A key-value store is the simplest database there is, which is why the interview is all about the hard parts: where each key lives, how many copies to keep, and what to do when copies disagree.

QuestionAssumptionWhy it matters
Operationsget, put, delete by key; no joins, no range scans across keysAny node can find a key by hashing it
Data10B keys, ~1 KB average, 1 MB max~10 TB before copies
Traffic1M ops/s at peak, 60% readsThroughput, not disk, sets the node count
Latencyp99 under 10 msCan't wait for the slowest copy
AvailabilityWrites must keep working when nodes or a link fail ("always writable")Picks AP over CP: eventual consistency, conflict handling
DurabilityNo acknowledged write is lostSeveral copies, commit log, repair
ConsistencyTunable per requestN, R and W quorums

The typical user is a shopping cart, a session, a user profile, or a feature flag: small values read by key, where losing a write is much worse than briefly reading an old one. If the product needs transactions across keys, this is the wrong tool; see Cassandra vs CockroachDB.

Estimates

  • Back of the envelope
  • Numbers
  • Storage: 10B × 1 KB = 10 TB. Three copies make 30 TB. Leave half again for compaction and growth: ~45 TB. At 2 TB of usable SSD per node, that is about 23 nodes.
  • Traffic: 1M ops/s = 600k reads + 400k writes. Each write goes to all 3 copies (1.2M replica writes). Each read touches 2 copies (1.2M replica reads). Total ≈ 2.4M replica operations a second.
  • Nodes: one node with an SSD and an LSM engine can do roughly 50k small operations a second with headroom. 2.4M ÷ 50k ≈ 48, so plan about 50 nodes, which also leaves room to lose a few.
  • Network: 2.4M × 1 KB ≈ 2.4 GB/s across the cluster, about 50 MB/s per node. Fine on 10 Gb/s links, before repair and streaming traffic.

API

  • Interface
get(key, consistency=QUORUM)          → { value | siblings[], context }
put(key, value, context, consistency=QUORUM) → ok
delete(key, context)                   → ok   (writes a tombstone)

consistency: ONE | QUORUM | ALL        (sets R or W for this call)
context:     opaque version (vector clock) returned by get,
             sent back on put so the store knows what you've seen

The context is the important part. A client reads, edits and writes back the context it read, which tells the store "this write replaces those versions". If two clients wrote from the same old version, the store keeps both and the next get returns siblings for the client to merge.

Architecture

  • Whole system
  1. Route: the client sends the request to any node (or straight to a replica, if the client library knows the ring). That node becomes the coordinator.
  2. Find replicas: the coordinator hashes the key to a point on the ring and walks clockwise to find N distinct nodes: the preference list.
  3. Fan out: it sends the request to all N and waits for W write acks or R read replies, then answers the client. The rest finish in the background.
  4. Converge: replicas that missed a write catch up through read repair, hinted handoff and Merkle-tree anti-entropy.

Partitioning: the ring

  • Deep dive 1
  • Sharding and consistent hashing
  • Hot partitions

With hash(key) mod nodes, adding one node moves almost every key. On a ring, adding a node moves only the keys in the ranges it takes over: about 1/n of the data.

  • The ring: hash every key into a big number space (for example 0 to 264−1) and bend it into a circle. Each node owns one or more points on the circle, called tokens. A key belongs to the first token clockwise from its hash.
  • Virtual nodes: with one token per node, ranges come out uneven, and a node that leaves dumps its whole range on one neighbour. Giving each node many tokens (vnodes) evens out the ranges and spreads a failed node's load across many peers. Cassandra used 256 per node for years and moved its default to 16 in version 4.0, with a smarter token picker, because fewer tokens make repair and streaming cheaper.
  • Bigger machines, more tokens: a node with twice the disk and CPU gets twice the tokens. That is how a mixed fleet shares load fairly.
  • Distinct replicas: when walking clockwise for N replicas, skip tokens that belong to a node already chosen, and with rack awareness, skip nodes in a rack already chosen. Three copies in one rack is one copy against a power failure.
  • Hot keys: the ring spreads keys, not traffic. One celebrity key still lands on N nodes. Cache it in front, or split it into sub-keys.
keys moved when node n+1 joins ≈ 1/(n+1) of all keys  ·  with mod-n hashing ≈ n/(n+1)

Replication and quorums

  • Deep dive 2
  • Consistency and CAP

Three numbers describe every request: N copies exist, a write waits for W of them, a read waits for R of them.

SettingWhat you getTypical use
N=3, W=2, R=2Read and write sets always overlap (2 + 2 > 3). Survives one node down for both reads and writes.The default
N=3, W=1, R=1Fastest, most available. Reads can be stale until replicas catch up.Metrics, click counts, caches
N=3, W=3, R=1Fast, fresh reads, but one dead node blocks all writes.Read-heavy data that rarely changes
N=3, W=1, R=3Writes never wait; reads are slow and fail if any copy is down.Rarely a good idea
R + W > N  →  every read set includes at least one copy of the latest acknowledged write
  • Waiting for the fastest: the coordinator sends to all N and returns after the first W or R answers. One replica stuck in a garbage-collection pause or a compaction doesn't slow the request. This is why quorums beat "always read the primary" on tail latency.
  • Read repair: if the R replies disagree, the coordinator returns the newest and writes it back to the stale replica. Hot keys repair themselves this way.
  • Sloppy quorum: Dynamo counts the first N healthy nodes on the ring, not the first N nodes. When a home replica is down, a stand-in accepts the write. Writes keep working, but now R + W > N no longer promises overlap, because the stand-in is not in the read set.
  • Not linearizable: even strict quorums can show a newer value to one reader and an older one to the next during a write in progress, and last-write-wins can drop writes. If you need compare-and-set, use a consensus-based store: Raft.

Try it: a quorum calculator

  • Lab

Pick how many copies to keep and how many must answer. Then knock replicas over and see what still works. The latency model: each replica answers in 2 ms, except 5% of the time it is stuck for 40 ms (a GC pause, a compaction). The coordinator waits for the R-th or W-th fastest of the replicas that are up.

Presets

Rough model: replicas fail and stall independently. Yearly availability assumes each node is up 99.9% of the time. "Stale read" is the chance a read, sent right after a write, reaches no replica that has it yet.

Conflicts and versions

  • Deep dive 3
  • Clocks and IDs

An always-writable store will accept two writes to the same key on two sides of a network split. When the split heals, something has to decide what the value is.

Last write wins

Every write carries a timestamp, and the highest timestamp wins. Simple, and it is what Cassandra does per column. The cost: two concurrent writes become one, silently, and a node whose clock runs ahead wins writes it shouldn't. Good for values that are replaced whole (a profile photo URL, a session blob); bad for values that are edited (a cart).

Vector clocks

Each version carries a list of (node, counter) pairs. Version X descends from Y if every counter in X is at least the one in Y. If neither descends from the other, they are concurrent, and the store keeps both as siblings.

StepWhat happensClock
1Asha adds a book; node A coordinates[A:1]
2Asha adds a lamp from her phone; A again[A:2]
3Network splits. Her laptop, still holding [A:1], adds a pen via node B[A:1, B:1]
4A read sees [A:2] and [A:1, B:1]. Neither descends from the other: siblings2 versions
5The cart app merges (book, lamp, pen) and writes with the combined context[A:3, B:1]
  • Who merges: the application, because only it knows that a cart merge is a union. The famous side effect: a deleted cart item can come back, because a union can't tell "removed" from "never added". Keep removals as tombstones, or use a data type built to merge, such as a CRDT set.
  • Clock growth: one entry per coordinating node. Dynamo trimmed the oldest entries past about 10; Riak later used dotted version vectors to avoid sibling explosions.
  • Interview answer: name both, pick LWW for whole-value data and vector clocks or CRDTs for data that is edited concurrently, and say what each one loses.

Failures and repair

  • Deep dive 4
  • Merkle trees

Three mechanisms, for three time scales: seconds, minutes to hours, and anything left over.

MechanismWhen it runsWhat it fixes
Read repairOn reads, when replies disagreeStale copies of keys people actually read
Hinted handoffWhile a replica is down, for a limited window (Cassandra's default is 3 hours)Writes missed during short outages, replayed when the node returns
Anti-entropy with Merkle treesScheduled, per key range (for example weekly)Everything else: cold keys, expired hints, lost hint stores
  • Merkle trees: each replica hashes its keys in a range into a tree, leaves up to a root. Two replicas compare roots; if equal, the range is in sync with one message. If not, they walk down only the subtrees that differ and stream just those keys. The Merkle trees page has a lab for tree depth.
  • Deletes: a delete writes a tombstone, not a hole, so repair can't resurrect the old value from a replica that missed it. Tombstones are purged after a grace period (10 days by default in Cassandra), so every range must be repaired more often than that.
  • Permanent loss: if a node is gone for good, operators remove it and the ring hands its ranges to other nodes, which stream data from the surviving copies. With vnodes, many peers share that streaming.

Membership and gossip

  • Deep dive 5

With no master, every node needs its own picture of who is in the cluster, who owns which tokens, and who is up.

  • Gossip: once a second, each node swaps state with a few random peers: its view of every node's status, tokens and a heartbeat counter, each with a version. Newer versions win. A change reaches all n nodes in about log2(n) rounds: 6 rounds for 50 nodes, 10 for 1,000.
  • Failure detection: a node is suspected when its heartbeats stop arriving on time. Cassandra uses a phi accrual detector, which turns "how late is this heartbeat compared with usual" into a suspicion level, so a slow network raises the bar instead of causing false alarms.
  • Down vs gone: a node marked down is a temporary state: hints pile up for it, and it is skipped for reads. Only an operator removes a node from the ring for good. Otherwise a 30-second network blip would trigger terabytes of data movement.
  • Seed nodes: a few well-known addresses that new nodes contact first to join the gossip. They are not special after that.
  • Joining: a new node picks tokens, announces them by gossip, and streams the data for its new ranges from the current owners. Reads keep going to old owners until streaming finishes.

Storage engine

  • Databases: LSM trees

Writes outnumber reads on many key-value workloads, and replicas take every write, so each node uses a log-structured merge tree, which turns random writes into sequential ones.

PieceJobNote
Commit logAppend every write, fsync in small batchesReplayed after a crash; deleted once flushed
MemtableSorted map in RAM of recent writesFlushed to disk at ~64–256 MB
SSTablesImmutable sorted files on diskA read checks the memtable, then newest files first
Bloom filtersSay "definitely not in this file"~10 bits per key for ~1% false positives
CompactionMerge files, drop overwritten values and old tombstonesUses disk I/O; size-tiered for writes, leveled for reads

Memory check: 10B keys × 3 copies ÷ 50 nodes = 600M keys per node. Bloom filters at 10 bits a key are about 750 MB per node, which fits in RAM.

Deployment

  • Operations
  • Racks and zones: spread the N copies across three availability zones, so losing a whole zone still leaves a quorum of 2.
  • Multi-region: keep N copies per region (for example 3 + 3) and use LOCAL_QUORUM, so requests wait only for nearby replicas and cross-region copying happens in the background. Use EACH_QUORUM only for the rare write that must be in both regions before you answer.
  • Rolling upgrades: one node at a time. With N=3 and quorum 2, one node down at a time is safe; hints cover its few minutes of downtime.
  • Adding capacity: add nodes before disks pass 50–60%, because compaction and streaming need free space. Add several at once with vnodes, and the load spreads evenly.

v2 ideas: per-key time-to-live, secondary indexes, change data capture to stream every write to Kafka, lightweight transactions (Paxos per key) for the few writes that need compare-and-set, and tiered storage for cold ranges.

"Keys are hashed onto a ring, and each node owns many small ranges through virtual nodes, so adding a node moves only its share of data. Each key is stored on the next three distinct nodes clockwise, across zones. Any node can coordinate a request: it sends to all three and waits for two, so R plus W is greater than N and reads see the latest acknowledged write, and one slow node never sets the latency. When a replica is down, a neighbour holds a hint and replays it later, and scheduled Merkle-tree repair catches anything hints missed. Concurrent writes are kept as siblings with vector clocks for data that's edited, or resolved by last-write-wins for data that's replaced whole. Membership spreads by gossip with a phi accrual failure detector, and each node stores data in an LSM tree with a commit log."
