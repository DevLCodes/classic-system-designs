Classic system design walkthrough

Web Crawler

Design a crawler for a search engine. Starting from a set of seed URLs, it should download 15 billion pages in four weeks, keep them fresh afterwards, never overload a website, respect robots.txt, and not get stuck in endless generated pages. Assume HTML only for now, but make it easy to add other content types.

Requirements

  • Clarify
  • Non-functional requirements

The basic loop fits on a whiteboard: take a URL, download it, find links, repeat. The design is about doing it 6,000 times a second while being polite, avoiding duplicates and not falling into traps.

QuestionAssumptionWhy it matters
Scale15B pages from ~1B websites in 4 weeksSets fetch rate, storage and frontier size
ContentHTML only for v1; images, PDFs and video laterFetching and processing must be pluggable by protocol and MIME type
ProtocolsHTTP and HTTPS; FTP possible laterProtocol modules chosen by URL scheme
PolitenessAt most one connection per host; a delay between requests; obey robots.txtOtherwise we are a denial-of-service attack and get blocked
FreshnessImportant pages revisited within hours to daysThe crawl never really ends
RobustnessMalformed HTML, slow servers, traps, crashes mid-crawlA four-week job must survive machine failures without starting over
ExtensibilityNew processors (indexer, link graph, spam detection) attach without changing the coreDownloaded documents are shared by several consumers

Out of scope: ranking and serving search results, and rendering JavaScript-heavy pages (a later, much more expensive tier with headless browsers).

Estimates

  • Back of the envelope
  • Numbers
  • Fetch rate: 4 weeks ≈ 2.4M seconds, so 15B ÷ 2.4M ≈ 6,200 pages a second. Plan for 2× that to absorb slow hosts and retries.
  • Concurrency: if a fetch takes about 1 s end to end (DNS, connect, slow servers), we need ~6,000–12,000 fetches in flight. With async I/O, a single machine handles hundreds to a few thousand, so a few dozen fetcher machines.
  • Storage: 15B × (100 KB page + 500 B metadata) ≈ 1.5 PB. Keeping storage at most 70% full means about 2.14 PB. Compression (HTML compresses 5–10×) cuts that a lot.
  • Dedupe sets: an 8-byte checksum per URL is 15B × 8 B = 120 GB, and the same again for content checksums. Too big for one machine's RAM comfortably, fine when sharded.

The crawler is an internal pipeline, so its "API" is mostly the contracts between components and the events it emits. Indexing, link-graph building and spam detection subscribe to page.fetched instead of being built into the crawler.

Architecture

  • Whole system

A worker runs the loop: take a URL from the frontier, resolve its host, check robots.txt, download into a document input stream (an in-memory buffer for pages up to ~64 KB, spilling to a temp file beyond that, so several processors can read the same page without fetching it again), run the content dedupe test, store the page, extract links, filter and dedupe them, and add the survivors to the frontier.

Protocol modules (HTTP, later FTP) are chosen by URL scheme, and processing modules by MIME type, so adding PDFs means adding a module, not changing the loop.

The URL frontier

  • Deep dive 1
  • Queues

The frontier decides what to fetch next. It has two jobs that pull against each other: fetch important pages first, and never hit one host too often.

  1. Front queues: priority. Incoming URLs are scored (link-based importance such as PageRank, how often the page changes, how long since the last fetch) and placed in one of several priority queues.
  2. Back queues: politeness. Each back queue holds URLs for exactly one host. A heap orders back queues by the earliest time each host may be contacted again.
  3. Selection. A worker pops the host whose time has come, takes its next URL, and after the fetch the host's next allowed time is set to now plus a delay (for example 10× the last response time, or the robots.txt crawl delay). When a back queue empties, it is refilled from the front queues, biased towards high priority.

This is the design of the Mercator crawler, and it gives both properties: at most one connection per host, and important pages first. Breadth-first order falls out naturally; a worker may go depth-first within one site to reuse a connection.

Size: hundreds of millions to billions of URLs, so the frontier lives on disk. Each queue keeps a small in-memory buffer at both ends: an enqueue buffer flushed to disk when full, and a dequeue buffer refilled from disk ahead of the workers.

Politeness, robots.txt and DNS

  • Deep dive 2
  • DNS
  • Rate limiting
  • robots.txt. Before crawling a host, fetch https://host/robots.txt and obey its User-agent, Disallow, Allow and (where supported) Crawl-delay rules. Cache the parsed rules per host for about a day, so it isn't fetched before every page.
  • One host, one worker. Hashing hosts to back queues and back queues to workers means a single worker ever talks to a given host. No coordination needed.
  • Back off on trouble. On 429 or 503 responses, or rising latency, lengthen that host's delay. A site that is struggling should see us slow down.
  • Identify yourself. A clear user agent with a contact URL, so site owners can reach you instead of blocking your IP range.
  • DNS caching. 6,200 fetches a second would mean thousands of DNS lookups a second, and standard resolver libraries are often synchronous. Run a local caching resolver per machine (respecting TTLs), and resolve asynchronously ahead of fetches. Without this, DNS becomes the bottleneck.

Seen it before?

  • Deep dive 3
  • Hashing

Two different checks, at two points in the loop.

CheckQuestionHow
URL seen, before adding to the frontierHave we already queued or fetched this URL?Normalize the URL (lowercase host, drop fragments and default ports, sort or strip tracking parameters), take a 64-bit hash, look it up in a sharded set, with a cache of popular URLs in front
Content seen, after fetchingHave we stored this exact page under another URL (mirrors, session ids)?Checksum of the content (a 64-bit hash, or MD5/SHA truncated) looked up in another sharded set; near-duplicates use SimHash

Each set is 15B × 8 bytes = 120 GB. A Bloom filter can hold the URL-seen set in a fraction of that: a bit array with k hash functions, where "not present" is certain and "present" is probably true. Its one flaw matters here: a false positive means a new URL is wrongly treated as seen and never crawled. Size the filter so that rate is tiny, or confirm positives against the exact store for important URLs.

Try it: size the URL-seen filter

  • Lab

Choose how many URLs the filter must remember and how many bits it spends per URL. The number of hash functions is set to the best value for that size.

False positive rate p = (1 − e−kn/m)k with the optimal k = (m/n)·ln 2. "Pages never crawled" assumes 5 billion genuinely new URLs are tested against the filter during the crawl. The exact store needs 8 bytes per URL.

Crawler traps

  • Governance

A trap is a set of URLs that never ends. Most are accidents of site design; some are deliberate, to catch spam crawlers.

TrapExampleDefence
Infinite calendars/calendar?date=2391-04-17, each page linking to the next dayPer-host page budget; pattern detection on URLs that differ only in a number
Query-parameter explosionsFaceted search: every combination of filters and sort ordersStrip or limit parameters; cap distinct URLs per path
Session ids in URLs?sid=8f3a… on every linkNormalize known session parameters; the content-seen test catches the rest
Cyclic paths/a/b/a/b/a/b/… from relative links or symlinksMaximum URL length and depth; repeated path segment detection
Generated junkPages created on the fly to waste crawler timeLow quality score lowers priority; per-host budgets based on importance

The strongest single signal is an impossibly large number of URLs for one host compared with its importance. Budgets per host, scaled by importance, turn every trap into a bounded cost.

Storage

  • Databases
  • Cassandra
urls  (Cassandra, partitioned by url_hash)
  url_hash      blob     PRIMARY KEY    -- 64-bit hash of the normalized URL
  url           text
  host          text
  last_fetched  timestamp
  next_fetch    timestamp
  content_hash  blob
  priority      float
  status        int      -- last HTTP status
  • Page bodies: compressed, in object storage or a distributed file system, batched into large files (WARC format, many pages per file) because billions of 100 KB objects are expensive to manage one by one.
  • URL metadata: billions of rows written at thousands a second and read by key: a wide-column store such as Cassandra, Bigtable or HBase. LSM storage suits the insert-heavy load, and tunable consistency is fine because a crawl tolerates slight staleness.
  • Seen sets: sharded in memory (Bloom filter or hash set) on the crawler machines that own those hosts, backed by the URL table.

Distributing the crawl

  • Consistent hashing

Partition everything by host. A consistent hash of the hostname picks the crawler node that owns that host's frontier queue, its URL-seen and content-seen shards, and its robots and DNS cache entries. Politeness then needs no coordination, and most lookups are local.

When an extractor finds a link to a host owned by another node, it batches those URLs and sends them to the owner. Most links on a page point to the same site, so cross-node traffic is a minority.

Failures: a four-week crawl will lose machines. Each node checkpoints its frontier and seen sets to remote storage every few minutes. When a node dies, consistent hashing hands its hosts to neighbours, which load the latest checkpoint and continue; a few minutes of work is redone, and the dedupe tests make that harmless.

Freshness and recrawling

  • Production

After the first pass the crawler becomes a scheduler: each URL's next fetch time depends on how often it has changed before and how important it is. A news homepage may be fetched every few minutes, an old blog post every few months.

  • Use conditional requests (If-Modified-Since, If-None-Match): an unchanged page costs a 304 with no body.
  • Read sitemaps, which list URLs with last-modified dates, and accept push notifications where sites offer them (such as IndexNow).
  • Compare the new content hash with the old one; emit page.changed only when it differs, so the indexer doesn't redo work.

"15 billion pages in four weeks is about 6,200 pages a second, 5 Gb/s and 1.5 petabytes. The frontier has priority queues in front and one queue per host behind, ordered by when each host may next be contacted, so we fetch important pages first and never hit a site with more than one connection. Workers use a local DNS cache and cached robots.txt rules. After fetching, a content checksum drops duplicates; extracted links are normalized, filtered and checked against a URL-seen set before going back into the frontier. Everything is partitioned by host with consistent hashing, so politeness needs no coordination, and nodes checkpoint so a failure costs minutes, not weeks."
