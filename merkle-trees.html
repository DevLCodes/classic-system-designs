Merkle trees

A tree of hashes that lets two machines find out which parts of a huge dataset differ by exchanging a handful of hashes instead of the data. It is how Cassandra and DynamoDB repair replicas, how Git and BitTorrent check content, and how sync tools find changed files.

The problem

Two replicas each hold a billion keys. A few thousand of them drifted apart after a node was down for an hour. How do you find those few thousand without sending a billion keys over the network?

Comparing one hash of the whole dataset tells you whether the replicas differ, not where. Comparing a hash per key tells you where, but means shipping a billion hashes. A Merkle tree sits in between: it hashes ranges of keys, then hashes those hashes, level by level, so you can start at the top and only walk down the branches that disagree.

The same idea shows up whenever you need to verify or sync big data cheaply: anti-entropy repair between replicas, Git commits, BitTorrent pieces, certificate transparency logs and blockchains.

How the tree is built

  1. Split the key space into ranges. In a database the ranges follow token order (the hash ring), so both replicas cut the same boundaries.
  2. Hash each range. A leaf is a hash over the keys and values (or versions) in that range.
  3. Hash pairs upward. Each parent is the hash of its children, until one root hash summarises everything.

The tree is small: with 215 (32,768) leaves it has about 65,000 hashes, about 1–2 MB, whatever the size of the data under it. Building it means reading the whole dataset once, which is the expensive part.

Comparing two trees

  1. Both replicas build a tree over the same range of keys and exchange root hashes.
  2. Equal roots: the replicas agree, done. One hash crossed the network.
  3. Different roots: exchange the two children's hashes and recurse only into the children that differ.
  4. At a differing leaf, stream the keys in that range (or their versions) and reconcile them: the newer write wins, or the conflict is resolved however the database resolves conflicts.

If d leaves differ in a tree of depth h, the walk compares at most about 2·d·h hashes. A handful of differences in a billion keys costs a few hundred hashes plus the keys in the few bad ranges.

hashes compared ≈ 1 + 2 · (differing leaves) · depth    data streamed ≈ (differing leaves) × (keys per leaf)

Choosing the tree size

TreeUpsideDownside
Shallow (few leaves)Tiny tree, cheap to build and hold in memoryEach leaf covers many keys; one changed key forces streaming the whole range ("overstreaming")
Deep (many leaves)Precise: streams little beyond what actually differsMore memory and more round trips to walk down
Per sub-range treesRepair a slice of the ring at a time, bounded memoryMore trees to build and schedule

Cassandra caps the depth (220 leaves by default in recent versions) and repairs one token range at a time to keep trees precise without unbounded memory. The other knob is how often to repair: the tree is built from a full scan, so a full repair is heavy disk and CPU work, typically scheduled weekly per node, and it must finish within the tombstone grace period (10 days by default in Cassandra) or deleted data can come back.

Failure modes

Deleted data comes back

A delete is a tombstone. If a replica missed the delete and repair doesn't run before tombstones are purged, the old value on that replica looks like the newest data and repair copies it back everywhere. Repair every node more often than the grace period.

Repair overloads the cluster

Building trees reads everything; streaming differences writes a lot. Throttle repair, run it a range at a time, and use incremental repair (only data written since the last repair) where it is reliable.

Trees that disagree for no reason

If replicas hash slightly different things (different range boundaries, data still being written while the tree is built), every leaf looks different and repair streams far more than needed. Snapshot or bound the time window, and make both sides cut the same ranges.

Weak hashes

For repair, a collision only means one missed difference, so speed matters more than strength. Where trees prove integrity to someone who might cheat (Git, certificate logs), use a cryptographic hash such as SHA-256.

Saying it in an interview

"Replicas can drift when a node misses writes, so besides read repair and hinted handoff I'd run anti-entropy with Merkle trees. Each replica hashes its token ranges into leaves and hashes pairs up to a root. Two replicas compare roots and only walk down branches that differ, so finding a few thousand bad keys in a billion costs a few hundred hashes plus streaming the few ranges that differ. Building the tree needs a full scan, so repair is throttled and scheduled per range, and it has to finish within the tombstone grace period or deletes can be undone."
