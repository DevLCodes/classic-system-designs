What a search engine does

A database index answers "which row has id 42?". A search index answers "which documents mention wireless noise cancelling headphones, and which of them are the best match?".

The naive way is WHERE body LIKE '%headphones%'. A pattern with a leading wildcard can't use a B-tree, so the database reads every row. That is fine for 10,000 rows and hopeless for 100 million. It also gets the meaning wrong: it misses "Headphone", matches "headphonesXYZ", and has no idea which match is better.

A search engine fixes this with work at write time. It splits each document into terms, and keeps a map from each term to the documents that contain it. A query then looks up a handful of terms instead of scanning every document.

The search index is almost never the source of truth. The database owns the data; the index is a derived copy, built to be queried by words, and rebuilt from the database whenever needed.

Tokens and analyzers

An analyzer turns text into terms. It runs in three steps: character filters clean the raw text (strip HTML, fold accents), a tokenizer splits it into tokens, and token filters change or drop tokens.

Tokenize"Noise-cancelling headphones!" → Noise cancelling headphonesSplit on spaces and punctuation. Languages without spaces (Chinese, Japanese, Thai) need dictionary or n-gram tokenizers.

Changing the analyzer changes which terms are in the index, so it means a full reindex. Pick it early, test it on real queries, and plan for reindexing (an index alias makes the switch instant; see Elasticsearch basics).

Not every field should be analyzed. A product title is text: analyzed, searchable by word. A SKU, a status or an email is a keyword: stored as one exact term, used for filters, sorting and facet counts.

The inverted index

A normal (forward) index maps a document to its words. An inverted index flips it: each term points to a posting list, the sorted list of document IDs that contain it. The set of all terms is the term dictionary.

What a posting list holds

  • Document IDs, sorted. Stored as gaps between IDs rather than the IDs themselves: 3, 7, 21, 22, 40 becomes 3, 4, 14, 1, 18, and small numbers pack into a few bits. Lucene packs blocks of 128 gaps using just enough bits for the largest one.
  • Term frequency: how often the term appears in each document, for scoring.
  • Positions (optional): where in the document each occurrence is, so a phrase query like "red shoes" can check that the words are next to each other. Positions often make the index twice as big, so turn them off on fields that never need phrases.

Answering a query

For red AND shoes, walk both sorted lists with two pointers and keep the IDs that appear in both. Start from the shortest list: if "red" has 2 million entries and "suede" has 3,000, the result can have at most 3,000. Skip pointers let the engine jump ahead in the long list instead of reading every entry.

The term dictionary itself has to be fast to look up. Lucene keeps it as a compressed prefix structure (a finite state transducer) small enough to sit in memory, so finding a term's posting list is a memory lookup plus, at most, one disk read.

Immutable segments

Posting lists are packed tightly and sorted, so editing them in place would be slow. Instead, new documents go into a new small segment, a complete mini-index that never changes once written. A query searches every segment and merges the results. A background job merges small segments into bigger ones, just like compaction in an LSM tree.

Because segments are immutable, a delete only marks the document as gone in a bitmap, and an update is a delete plus a new insert. The space comes back when segments merge. A workload that updates the same documents all day (prices, stock counts) makes a lot of merge work.

      Ranking with BM25

      Matching gives a set of documents. Ranking decides the order, and users rarely look past the first ten. Three ideas carry most of the weight:

      • Term frequency. A document that says "kafka" five times is probably more about Kafka than one that says it once. But not five times more.
      • Inverse document frequency. A rare term tells you more than a common one. In a million documents, a term found in 1,000 of them has an IDF of about 6.9; a term found in half of them has about 0.7. The rare word counts ten times as much.
      • Length normalization. One mention in a 20-word title means more than one mention in a 5,000-word manual.

      The older TF-IDF formula multiplies the first two. BM25, the default in Lucene, Elasticsearch, OpenSearch and Solr, adds saturation and length normalization. For each query term in a document:

      score = IDF × tf × (k1 + 1) / (tf + k1 × (1 − b + b × doclen / avgdoclen))
      IDF = ln(1 + (N − n + 0.5) / (n + 0.5)) N = docs in the index, n = docs with the term

      The document's score is the sum over the query terms. Two knobs:

      KnobDefaultWhat it does
      k11.2How fast repeats stop helping. For an average-length document the tf part is 1.0 at one mention, 1.38 at two, 1.77 at five and 1.96 at ten, and can never pass k1 + 1 = 2.2. Keyword stuffing hits a ceiling.
      b0.75How much length matters. 0 ignores length; 1 fully divides by relative length.

      Beyond text relevance

      BM25 only knows about words. Real ranking mixes it with other signals: popularity, freshness, ratings, price, the user's location. A common shape is two stages: a cheap first pass (BM25 plus filters) picks the top few hundred candidates per shard, then a heavier model reranks only those. Many systems now add a vector search beside BM25 and merge the two lists (hybrid search), because embeddings catch meaning ("cheap flights" ≈ "low-cost airfare") while BM25 catches exact words, part numbers and names.

      Sharding a search index

      One machine can hold an index of tens of millions of documents. Past that, or for more query throughput, you split it. There are two ways to split an inverted index.

      By document (local index)By term (global index)
      Each shard holdsA full index over a slice of documentsThe full posting lists for a slice of terms
      A query touchesEvery shard (scatter-gather)Only the shards that own its terms
      A write touchesOne shardOne shard per distinct term in the document, often dozens
      Multi-term ANDDone inside each shardPosting lists, possibly millions of IDs long, cross the network to be intersected
      RankingEach shard scores locally; IDF differs a little per shardExact global statistics
      Hot spotsEven, if documents are spread by hashPopular terms make hot shards

      The cost of sharding by document is tail latency. A query is as slow as its slowest shard. If each shard has a 1% chance of a slow response, a query fanned out to 20 shards hits at least one slow shard 18% of the time (1 − 0.9920). Fixes: keep the shard count modest, add replicas and send a backup request when a shard is late, and set a timeout that returns partial results rather than waiting.

      Replicas are how a search cluster scales reads: each shard has copies on other nodes, and any copy can answer a query. More shards help with data size and indexing speed; more replicas help with query throughput and survive node failures. Global term statistics matter less than they sound: with documents spread by hash, each big shard sees nearly the same term frequencies.

      A search with a strong filter can skip the fan-out. If every query is scoped to one tenant, route by tenant ID so a query hits one shard, as in sharding. Watch for a tenant that outgrows its shard (see hot partitions).

      Near-real-time refresh

      Writing a new segment and making it searchable is not free, so engines batch it. Elasticsearch is "near real time": a new document becomes searchable about one second after it is written.

      • Refresh (default every 1 s) turns the in-memory buffer into a new segment that queries can see. It does not fsync; the new segment lives in the OS page cache.
      • Translog: every write is also appended to a log and, by default, fsync'd before the write is acknowledged. If the node crashes, it replays the log.
      • Flush commits segments to disk and trims the log.
      • Merge combines small segments so a query doesn't search hundreds of them.

      The trade-off is freshness against indexing cost. Refreshing every second creates many tiny segments and lots of merging. For a bulk load, turn refresh off (refresh_interval: -1) and replicas to zero, then restore both at the end. For a user who must see their own edit straight away, ask that one write to wait for the next refresh (refresh=wait_for), or show the edit from the database rather than the index.

      Keeping the index in sync with the database

      Writing to the database and the index from the application (a dual write) drifts apart the first time one write fails. The reliable pattern is change data capture: read the database's change log (with Debezium, for example) into Kafka, and have an indexer consume it and write to the search engine. Use the database row version as the document version, so an old event that arrives late can't overwrite a newer one. Keep a full reindex job ready, because you will need one after every analyzer or mapping change. See queues and the outbox pattern.

      Elasticsearch basics

      Elasticsearch (and its fork OpenSearch) wraps the Lucene library in a distributed service with a JSON API. Each Elasticsearch shard is a Lucene index made of segments.

      TermMeaningRough SQL analogue
      IndexA named collection of documents with one mappingTable
      DocumentA JSON object with an _idRow
      MappingField types: text (analyzed), keyword (exact), numbers, dates, geo pointsSchema
      ShardOne slice of an index. Primaries take writes; replicas are copies that serve reads and take over on failure.Partition
      Node, clusterA server; a group of servers with an elected master that tracks where shards liveDatabase cluster
      AliasA name that points at one or more indexesView

      Things that matter in a design:

      • The primary shard count is fixed when the index is created. Changing it means reindexing (or the split and shrink APIs, which only multiply or divide it). Elastic's guidance is shards of roughly 10 to 50 GB. Too many small shards waste memory and slow every query; too few big ones make recovery slow.
      • Query vs filter. match analyzes the input and scores; term looks up one exact term. Inside a bool query, clauses in must and should affect the score, while clauses in filter only include or exclude and can be cached. Put "in stock", "price under 100" and "tenant = 42" in filter.
      • Aggregations count and bucket the matching documents: "Brand: Sony (120), Bose (85)". They power the facets beside search results and read from column-oriented doc values, not the inverted index.
      • Zero-downtime reindex: build products_v2 next to products_v1, replay changes into both, then move the products alias in one atomic step.

      How search fails

      Deep pagination

      Page 500 with 20 results a page asks each shard for its top 10,000 results, then the coordinator sorts all of them to keep 20. Cost grows with the page number times the shard count. Elasticsearch refuses past 10,000 results by default (index.max_result_window). Use search_after with the last result's sort values for "next page", and cap how deep users can go.

      Index out of sync with the database

      A dropped event or a failed dual write leaves a product that is sold out in the database but "in stock" in search. Use change data capture with versions, alert on indexer lag, and run a periodic job that compares counts or checksums and repairs the difference. Re-check critical facts (price, stock) against the database at the moment of purchase.

      Too many shards or mapping explosion

      Thousands of tiny shards, or a mapping that grows a new field for every user-supplied key, eat cluster memory and slow the master. Size shards to tens of GB, put arbitrary keys in a flattened field or a key/value pair, and leave dynamic mapping off for user data.

      Expensive queries

      A leading wildcard (*phone), a regex, or a huge terms list can scan the whole term dictionary. One bad query can slow the whole cluster. Block or rewrite them at the API layer, set timeouts, and use n-gram fields when you really need infix matching.

      Relevance quietly getting worse

      A ranking change ships, nothing errors, and click-through drops 5%. Keep a set of judged queries and measure precision and NDCG on every change, then A/B test ranking changes on live traffic before rolling them out.

      Indexing load starving queries

      Bulk indexing, frequent refreshes and heavy merges compete with queries for CPU and disk. Throttle bulk jobs, lengthen the refresh interval for write-heavy indexes, or separate indexing and query work onto different nodes or replicas.

      Saying it in an interview

      "Search won't run on the main database: a leading-wildcard LIKE scans every row and can't rank. I'd keep Postgres as the source of truth and feed an Elasticsearch index through change data capture into Kafka, with the row version as the document version so late events can't overwrite newer ones. Titles and descriptions are analyzed text fields; brand, category and stock are keyword fields used as filters and facets. Ranking starts with BM25 and adds popularity and freshness in a rerank step. I'd shard by document, since that keeps writes on one shard; with 200 GB of index that's about 8 primaries of 25 GB, plus replicas for query load. New products show up within about a second thanks to the refresh interval, and I'd use search_after instead of deep page numbers."
