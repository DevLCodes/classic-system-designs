Layers and encapsulation

The OSI model splits networking into seven layers; the internet really runs on four. Each layer wraps the one above it in its own header, and the receiver unwraps them in reverse.

For system design, three layers matter: network (IP: where a packet goes), transport (TCP or UDP: how reliably), and application (HTTP, gRPC, WebSocket, SMTP, DNS: what the bytes mean). Load balancers are described by the layer they read: an L4 balancer sees IPs and ports, an L7 balancer reads HTTP paths and headers. See load balancing.

TCP and UDP

TCPUDP
ConnectionHandshake first (SYN, SYN-ACK, ACK: 1 round trip)None: just send
DeliveryReliable and in order: numbered segments, acknowledgements, retransmitsBest effort: packets can be lost, duplicated or reordered
Flow and congestion controlYes: slows down when the receiver or network is overloadedNo: the application must behave
Head-of-line blockingOne lost segment stalls everything behind itNone
Use forWeb, APIs, databases, file transfer, emailDNS lookups, voice and video calls, games, QUIC (HTTP/3)

Rule of thumb: use TCP unless a late packet is worthless. In a video call, a frame that arrives 300 ms late is useless, so retransmitting it only adds delay; UDP lets the app skip it and move on.

HTTP/1.1, HTTP/2, HTTP/3

VersionRuns onKey changeStill hurts
HTTP/1.1TCPKeep-alive: reuse a connection for many requestsOne request at a time per connection, so browsers open ~6 connections per host
HTTP/2TCP + TLSMultiplexing: many requests interleaved on one connection; binary framing; header compressionOne lost TCP packet still stalls every stream on that connection
HTTP/3QUIC over UDPStreams are independent, so loss on one doesn't block others; TCP and TLS handshakes merged into one round trip; connections survive a phone switching from Wi-Fi to mobile dataSome networks block or throttle UDP, so clients fall back to HTTP/2

HTTPS is HTTP inside TLS. The TLS handshake proves the server's identity with a certificate and agrees on keys for encryption; TLS 1.3 needs one round trip, and resumed sessions can send data immediately. Terminate TLS at the load balancer or CDN, near the user, and use plain or internal mTLS traffic behind it. The full cost of a cold call is on numbers to know.

REST, GraphQL and gRPC

RESTGraphQLgRPC
ShapeResources and verbs: GET /orders/42One endpoint; the client sends a query naming exactly the fields it wantsTyped functions defined in a .proto file: GetOrder(OrderId)
PayloadJSON, human-readableJSONProtocol Buffers: binary, typically 3–10× smaller than JSON and faster to parse
TransportHTTP/1.1 or 2HTTPHTTP/2, with client, server and two-way streaming
CachingEasy: HTTP caches and CDNs understand GETHard: everything is a POST to one URLNone built in
Strong atPublic APIs, simple and stable contractsMany client screens with different data needs; avoids over- and under-fetchingService-to-service calls inside your network
Weak atChatty clients making many round tripsExpensive queries a client can write; needs depth and cost limitsBrowsers need a proxy (gRPC-Web); not human-readable

A common split: REST (or GraphQL) at the edge for apps and partners, gRPC between internal services. An order service that receives a REST call converts it to a gRPC call to the payment service; the generated client stub makes the remote call look like a local function, and the binary encoding over one multiplexed HTTP/2 connection keeps it cheap.

Whatever the style, make writes safe to retry: accept an idempotency key on POSTs that create things, version the API (/v2/ or a header), and paginate with cursors, not offsets.

Pushing updates to clients

MethodHowGood forCost
Short pollingClient asks every N secondsRare updates, simple clients, a few usersWasted requests; delay up to N
Long pollingServer holds the request open until there is data (or ~30 s), then the client asks againPush behaviour where WebSockets are blockedOne held request per client; reconnect after every message
Server-sent events (SSE)One long HTTP response streaming events; built-in reconnect with last event IDOne-way feeds: scores, notifications, live comments, LLM token streamsServer to client only
WebSocketHTTP request upgraded to a full-duplex connection over TCP, with light framing; wss:// adds TLSChat, collaboration, games: both sides send oftenStateful gateways; reconnect storms after deploys; harder through some proxies
WebhookServer-to-server: you register a URL; the provider POSTs to it when something happensPayment results, Git pushes, third-party eventsYou must expose and secure an endpoint; calls can be lost or repeated

A webhook replaces polling between companies. Instead of your payment service asking the processor "is it done yet?" every few seconds, the processor calls POST /webhooks/psp when the payment settles. Three rules: verify the signature on every call, handle each event idempotently by its event ID (providers retry), and run a reconciliation job that polls anything still pending after an hour, because a webhook can be lost. See payments.

Try it: polling vs push

Clients watching a live score. Change how many are watching, how often the score really changes, and the polling interval, and compare the load and delay of each method.

Method

Simple model: long polls time out after 30 s; push sends a 30 s heartbeat; a server handles about 10,000 requests a second or 100,000 idle connections.

How it goes wrong

Reconnect storms

Deploy a WebSocket gateway and a million clients reconnect in the same second, each doing TCP, TLS and auth. Drain connections slowly during deploys and make clients reconnect with exponential backoff plus random jitter.

Idle connections dropped silently

NATs, mobile networks and load balancers drop connections idle for 30 to 350 seconds without telling either end. Send a heartbeat every 20 to 30 seconds and treat two missed ones as a disconnect.

Chatty APIs over long distances

Ten sequential calls at 150 ms round trip is 1.5 s before any work. Batch, use GraphQL or a backend-for-frontend endpoint that gathers everything a screen needs, or move the work near the user.

Retries without idempotency

A timeout doesn't mean the request failed; it may have succeeded and only the reply was lost. Retrying a non-idempotent POST creates duplicates. Send an idempotency key and dedupe on the server.

Saying it in an interview

"Clients talk to us over HTTPS with REST, terminated at the edge; internal services use gRPC with protobuf over HTTP/2 because it's compact, typed and multiplexed. For live updates the server pushes over a WebSocket, falling back to SSE or long polling where WebSockets are blocked; polling every few seconds would mean millions of mostly empty requests. Gateways are stateful, so I keep a user-to-gateway map in Redis, send heartbeats every 25 seconds, and have clients reconnect with jittered backoff. For third-party events like payment results I take webhooks, verify signatures, dedupe by event ID, and reconcile anything still pending."
