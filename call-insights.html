Classic system design walkthrough

Call Insights

A sales platform's reps make video calls all day on Zoom, Google Meet and Teams. Build a system that collects every recording, transcribes it, analyses how the call went (sentiment, objections, next steps), links it to the right account or deal, and shows the insights to the rep and their manager within 30 minutes of the call ending. 10,000 reps make 4–5 calls a day, about 50 minutes each.

Requirements

  • Clarify
  • Non-functional requirements

This is a data pipeline more than a web service: third-party sources, heavy media files, expensive GPU steps, and a soft deadline per item. Eventual consistency is fine; losing a call or leaking one is not.

Estimates

  • Back of the envelope
  • Numbers
  • Calls: 10k reps × 5 = 50k calls a day; × 50 minutes = 2.5M minutes ≈ 42k hours of recordings.
  • Storage: at ~0.5 GB per hour of 720p video, that is about 21 TB a day, or about 7.6 PB a year if we kept every video. Audio alone is ~30 MB an hour, about 1.3 TB a day, and transcripts are tiny (~50 KB per call). So: keep video briefly, keep audio and transcripts longer. (A rough note that worked this out as 4 TB a day was off by about 10×.)
  • Peak: calls cluster in working hours. If 70% end in an 8-hour window, the peak hour sees ~4,400 calls, about 3,600 hours of audio to process in that hour.
  • GPU: a modern speech model on one GPU, with batching, transcribes roughly 30–50× faster than real time. At 40×, 42k hours a day is ~1,050 GPU hours a day; covering the peak hour within the deadline takes about 90–100 GPUs (the lab shows the curve).

Interfaces

  • Interface
  • Webhooks
// inbound, from vendors
POST /webhooks/zoom          { event: "recording.completed", meeting_id, download_url, … }
POST /webhooks/teams | /webhooks/meet

// internal workflow contract (one per step)
step(call_id, input_uri) → { status, output_uri, metrics }   // idempotent by (call_id, step)

// outbound, to the app
GET  /api/calls?deal_id=…&since=…
GET  /api/calls/{id}         → { transcript_uri, summary, sentiment, topics[], next_steps[], deal_id }
GET  /api/deals/{id}/signals → { risk: 0.31, momentum: "up", recent_calls: [...] }

Each pipeline step takes a call id and an input location and writes an output location, so steps are independent, testable and replaceable. Making every step idempotent by (call_id, step) means a retry or duplicate message just overwrites the same output.

Architecture

  • Whole system

Getting the recordings

  • Deep dive 1
  • Rate limits
  • Connect once per tenant: an admin authorizes our app with each vendor (OAuth). Tokens are stored encrypted and refreshed automatically.
  • Webhooks first: Zoom sends recording.completed with a download URL; Teams and Meet have their own notification APIs. Verify each webhook's signature, store the event, and return 200 immediately. Processing happens later.
  • Polling as a safety net: webhooks get lost. A reconciler lists each tenant's recent recordings every 15 minutes and enqueues any we have not seen.
  • Dedupe: the vendor's recording id is the idempotency key, so a webhook delivered three times and also found by the reconciler starts one workflow.
  • Respect vendor limits: download with a per-tenant and per-vendor token bucket, and back off on 429s. Download URLs expire, so fetch soon, and stream straight into object storage rather than through memory.

Choosing the pipeline style

  • Deep dive 2
  • Queues
OptionHowVerdict
Batch jobs over filesRecordings land in time-partitioned folders; cron jobs pick up new files for each step and write outputs next to themSimple to build. Failure handling, per-call deadlines and visibility are hard; cron intervals add latency
Queues between stepsEach step consumes a queue and publishes to the next; failures go to dead-letter queuesBetter visibility and retries. The overall state of one call is spread across queues
MonolithOne service runs every step for a callEasy at first; can't scale GPU and CPU steps separately, one bug stalls everything
Event pub/subSteps emit events; any number of subscribers reactEasy to add new feature extractors. Contracts drift; needs schema registry and contract tests
Workflow engine + task queuesA durable workflow per call (Temporal, AWS Step Functions, Airflow for batch) calls activities that run on worker poolsMy pick: per-call state, retries with backoff, timeouts and deadlines are built in, and each step's pool scales on its own

The engine's workflow for a call is a few lines of code: download, extract, transcribe, then run insight models in parallel, then match and publish. Retries, timeouts and "where is call X right now?" come for free. Events still go out at the end (call.insights.ready), so other products can subscribe without touching the pipeline.

Transcription and insights

  • Deep dive 3
  1. Extract: pull the audio track with ffmpeg, normalize it to 16 kHz mono, and optionally sample video frames (for slides or engagement signals). Cheap CPU work.
  2. Transcribe: a speech recognition model on GPUs, plus diarization to label who spoke when. Vendor speaker metadata (Zoom knows who was talking) improves labels. Batch several calls per GPU for throughput; split long calls into chunks for parallelism.
  3. Analyse: on the transcript, run models for sentiment per speaker over time, talk-to-listen ratio, questions asked, competitor and pricing mentions, objections and next steps. A large language model can produce a summary and action items; smaller classifiers are cheaper for fixed labels.
  4. Score: combine signals across a deal's recent calls into risk or momentum.

Store model name and version with every output. When a better model ships, reprocess recent calls in the background at low priority, without disturbing the 30-minute path for new ones.

Build or buy? Hosted speech APIs are quick to start and charge per minute. At 2.5M minutes a day, self-hosting an open model on our own GPUs is usually much cheaper, at the cost of running a GPU fleet. A common path is to start with an API and move once volume justifies it.

Try it: size the GPU pool

  • Lab

Transcription is the slow, expensive step. Choose call volume, how fast one GPU transcribes, and how many GPUs run during the peak hour, and see whether calls still get insights within 30 minutes.

Calls average 50 minutes; 70% end within 8 business hours. Download, extraction, insights and matching add about 6 minutes per call. Queueing uses a standard multi-server approximation, so treat the numbers as rough.

Linking calls to deals

  • Joins

The vendor tells us the participants' names and emails. The matcher:

  1. Separates internal participants (our customer's domain) from external ones.
  2. Looks up external emails as CRM contacts, then their accounts; falls back to matching the email domain to an account.
  3. Among that account's open deals, picks the one the rep owns or that is in an active stage; uses the calendar event title as a tie-breaker.
  4. Records a confidence. Low-confidence matches are shown to the rep to confirm with one click, and the confirmation trains the matcher.

Keep a synced copy of the needed CRM fields (contacts, accounts, deals) rather than calling the CRM per call; CRM APIs have tight rate limits too.

Lifecycle rules move and delete objects automatically. Deleting video after 30 days instead of keeping it cuts storage from petabytes a year to under a petabyte at any time.

Security and privacy

  • Governance
  • Tenant isolation: every object path, row and index document carries a tenant id; the API enforces it on every query, and large customers can get separate encryption keys.
  • Least privilege: workers get short-lived credentials scoped to the one object they process. Vendor OAuth tokens live in a secrets manager.
  • Who sees what: reps see their own calls, managers their team's, admins everything in their tenant. Every access is logged.
  • Consent and regulation: recording consent rules differ by country and state; respect opt-outs, support deletion requests across every store, and keep data in the customer's region if required.
  • PII in transcripts: optionally redact card numbers and similar before storing or sending text to any third-party model.

Failure handling

  • Production
  • Worker crash: long tasks send heartbeats; a missed heartbeat makes the engine retry the task elsewhere. Idempotent outputs make that safe.
  • Vendor trouble: 429s and 5xx retry with exponential backoff and jitter; the reconciler catches anything missed.
  • Bad input: after N attempts, the call goes to a dead-letter queue with the error, an alert fires, and an operator can replay it once fixed.
  • Backlog: if the GPU queue grows, scale out; if it can't, prioritize recent calls over reprocessing and tell users insights are delayed.

"About 42,000 hours of calls a day, mostly in business hours, with a 30-minute deadline. Vendor webhooks, backed by a polling reconciler, trigger an ingestion service that streams each recording into per-tenant object storage and starts a durable workflow keyed by the recording id. The workflow runs idempotent steps on separate pools: CPU for audio extraction, GPUs for transcription and diarization, then insight models in parallel and a CRM matcher. Failures retry with backoff, and persistent ones go to a dead-letter queue for replay. I'd size about 100 GPUs for the peak hour, keep video 30 days but audio and transcripts longer, and enforce tenant isolation at every layer."
