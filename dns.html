DNS

The internet's phone book: it turns a name like api.shop.com into an IP address, through a hierarchy of servers and caches. It is also the first load balancer and the first thing to break in a regional failover.

What DNS does

Before a browser can open a connection to api.shop.com it needs an IP address. DNS is a distributed, heavily cached database that answers that question in a few milliseconds when cached and tens of milliseconds when not.

DNS is not one server. It is a hierarchy of name servers, each responsible for a slice of the namespace, plus recursive resolvers (run by ISPs, companies, or public services such as 1.1.1.1 and 8.8.8.8) that do the legwork and cache answers. Answers are stored as resource records, the smallest unit you can ask for. Lookups normally use UDP on port 53, because a question and answer fit in one packet each; large answers and zone transfers use TCP.

A CNAME can't sit at the bare domain (shop.com) because that name must also hold NS and other records. DNS providers offer an ALIAS or "CNAME flattening" record that resolves the target themselves and returns A records.

How a lookup works

  1. Stub resolver. The OS checks its own cache and hosts file, then asks the configured recursive resolver.
  2. Root. If the resolver knows nothing, it asks a root server, which replies with the servers for .com. The 13 root names are served by over a thousand machines worldwide through anycast.
  3. TLD. The .com servers reply with the authoritative name servers for shop.com (its NS records).
  4. Authoritative. The organisation's own DNS (or its DNS provider) returns the A record and a TTL. The resolver caches it and answers the client.

Caching and TTLs

Every answer carries a time to live in seconds. Browsers, operating systems and resolvers cache it that long, which is why DNS can serve the whole internet. The same TTL decides how fast a change spreads: if api.shop.com has a 1-hour TTL and you move it to a new IP, some users keep going to the old address for up to an hour, and longer if a client ignores TTLs (some do).

TTLUse for
30–60 sRecords you fail over automatically (health-checked regional endpoints)
5 minA reasonable default for service endpoints
1 h – 1 dayThings that never move: MX, TXT verification, NS

Planning a migration? Lower the TTL to 60 s a day or two before the change, so caches already hold short TTLs when you switch; raise it again afterwards. Failed lookups are cached too (negative caching, set by the zone's SOA record), so a typo'd record can linger after you fix it.

Try it: pick a TTL

Your API's record is cached by resolvers all over the world. A shorter TTL makes failover faster but sends more queries to your authoritative servers and makes more users wait for a fresh lookup.

Clients

Simple model: each resolver refreshes once per TTL while it has traffic; a failover is detected in 30 s; a cold lookup costs about 40 ms.

DNS as a traffic router

Because the authoritative server chooses the answer, it can choose a different answer per user. Managed DNS services turn this into routing policies:

PolicyAnswers withUse for
Simple / round robinSeveral A records, shuffledCrude spreading; clients often stick to the first IP
WeightedRecords in proportion to weightsShifting 5% of traffic to a new region or stack
Latency or geoThe region nearest the resolver (or the client subnet, with EDNS Client Subnet)Multi-region apps, data residency
FailoverThe primary while its health check passes, else the secondaryActive-passive regions

DNS routing is coarse: it sees the resolver, not the user, and it is slowed by caching. So DNS usually picks a region or a CDN, and an L4/L7 load balancer spreads load inside it. Anycast goes further: many sites announce the same IP address and internet routing delivers each packet to the nearest one, which is how public resolvers, root servers and CDNs absorb huge traffic and attacks.

How DNS fails

Your DNS provider goes down

If nobody can resolve your name, a perfectly healthy service is unreachable. In 2016 an attack on the Dyn DNS provider made many large sites unreachable for hours. Use a provider with anycast at scale, and for critical domains consider two providers serving the same zone.

Failover slower than expected

Health check interval + TTL + clients that cache longer than the TTL (some runtimes cached DNS forever by default) means a "60-second" failover can take many minutes for part of your users. Test it, and keep long-lived connections able to reconnect.

Lookups in the hot path

A service that resolves a hostname on every outbound call adds latency and hammers its resolver; a crawler resolving millions of hosts can melt one. Cache lookups in process (respecting TTLs) or run a local caching resolver.

Dangling records

A CNAME left pointing at a deleted cloud resource can be claimed by someone else (subdomain takeover). Remove records when you delete what they point to.

Saying it in an interview

"Users resolve api.shop.com through a managed, anycast DNS provider with latency-based routing to our nearest healthy region; within a region an L7 load balancer spreads requests. The record has a 60-second TTL so a failed region drains in a minute or two, at the cost of more lookups, which the provider absorbs. Static content is a CNAME to the CDN. For a planned migration I'd drop the TTL a day early. Internally, services cache DNS answers in process so lookups never sit on the hot path."
