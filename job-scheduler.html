Distributed Job Scheduler

Design a job scheduler for a whole company, like cron for thousands of teams: a team registers a job that runs once at a set time or on a cron schedule, and a fleet of workers runs it. Plan for 10 million scheduled jobs and about 50 million runs a day, with a spike at the top of every hour. Runs should start within a few seconds of their time, no run may be silently lost, and one noisy team must never starve the others.

Requirements

  • Clarify
  • Non-functional requirements

A scheduler makes two promises: a job runs close to its time, and it runs, even when machines die. The hard part is keeping both promises for millions of jobs that mostly want the same few seconds.

FeaturesOne-off jobs at a time, cron schedules with a time zone, run now, pause, run history, retriesTwo kinds of trigger, one run path
Jobs10M registered, ~1 KB eachFits in one sharded database

Out of scope: workflows with many dependent steps (a DAG engine sits on top of this; see the workflow engine in Call insights), and the code inside each job. The scheduler starts a job by calling an HTTP endpoint, putting a message on a queue, or launching a container.

Estimates

  • Back of the envelope
  • Numbers
  • Runs: 50M a day ÷ 86,400 s ≈ 580 runs a second on average.
  • In flight: Little's law says runs in flight = start rate × time each run takes. 580/s × 20 s ≈ 11,600 runs at once, so plan around 35k worker slots (3× headroom).
  • The spike: 1M runs due at 02:00:00. With 35k slots and 20 s runs the fleet finishes 35,000 ÷ 20 = 1,750 runs a second, so the last of those runs starts about 1,000,000 ÷ 1,750 ≈ 570 s (almost 10 minutes) late. Spreading, priorities and scaling up before the hour are what bring that down.
  • Storage: jobs are 10M × 1 KB = 10 GB. Each run leaves ~500 bytes of history, so 50M × 500 B = 25 GB a day, or 750 GB for 30 days.
  • Scheduler reads: ~580 due jobs a second come out of an index on next_run_at. Tiny, as long as we read them in batches, a minute ahead.

The run id is the job id plus the scheduled time. If the same slot is ever fired twice, both copies get the same run id, and the second one is ignored. The fence number goes up each time a run is handed to a new worker, so a worker that lost its lease can't overwrite the result of the worker that took over.

Architecture

  • Whole system

Cron at scale

  • Deep dive 1
  • Sharding
  • Leader election

Classic cron is one process on one machine reading one file. At 10 million jobs, the schedule moves into a database, and many schedulers split it between them.

  • Store the next time, not just the rule: keep the parsed cron rule, its time zone, and a precomputed next_run_at in UTC. When a run fires, compute the next one from the scheduled time, not from "now", so small delays never add up into drift.
  • Partition the work: hash each job into one of, say, 1,024 partitions. Each scheduler holds a lease on some partitions in etcd or ZooKeeper; if it dies, its partitions move to another scheduler within seconds. Each partition has exactly one owner, so two schedulers don't fire the same job.
  • Read a minute ahead: once a minute, each owner runs SELECT job_id, next_run_at FROM jobs WHERE partition = ? AND next_run_at < now() + interval '60 s' AND NOT paused. With 580 due jobs a second across 1,024 partitions, that is about 34 rows per partition per minute.
  • Time zones and daylight saving: India has no daylight saving, but tenants elsewhere do. On the spring-forward day 02:30 doesn't exist, and on the fall-back day 01:30 happens twice. Pick a rule and document it: run a missing time at the next valid minute, and run a doubled time once.
  • Misfires: if a partition had no owner for 20 minutes, a job that runs every minute missed 20 slots. Let the job choose: run_once (default, one catch-up run), catch_up (all 20, for billing-style jobs), or skip.
  • Spread the top of the hour: offer a hashed minute (Jenkins writes it H * * * *: the job's id picks a fixed minute) or a window (any time between 02:00 and 02:15). Most nightly jobs don't care about the exact second, and asking turns a 1M-run spike into a gentle 15-minute slope.

Time buckets and the timing wheel

  • Deep dive 2
  • Queues

Asking the database "what is due now?" every second for every partition works, but it is wasteful. Two layers do better: coarse buckets on disk, fine slots in memory.

  • Buckets on disk: the index on (partition, next_run_at) already acts as minute buckets: one range read per partition per minute returns everything due in that minute.
  • Wheel in memory: drop each loaded job into slot second(next_run_at) of a 60-slot ring. Each second the hand moves one slot and every job in it fires. Inserting and cancelling are O(1); a min-heap would cost O(log n) per insert and pop, which is fine for 100k timers but adds up at millions with frequent cancels.
  • Hierarchical wheels: for timers far in the future, stack wheels: seconds, minutes, hours. A job sits in the hour wheel, drops into the minute wheel when its hour comes, then into the seconds wheel. Netty's HashedWheelTimer and Kafka's delayed-request handling use this idea.
  • Firing safely: in one transaction, insert the run row (INSERT … ON CONFLICT (run_id) DO NOTHING), move next_run_at forward, and write an outbox row for the due queue. A crash between steps can't lose a run or create two.
  • The wheel is only a cache: if a scheduler restarts, the new owner reloads the current minute from the database. Runs that were already fired hit the unique run id and are skipped.

Workers and leases

  • Deep dive 3
  • Consistency
  • Seat holds that expire

A worker never owns a run forever. It borrows it for a short time and keeps saying "still on it". If it goes quiet, the run goes back to the queue for someone else.

-- claim one run (many workers can run this at once without blocking each other)
UPDATE runs SET state = 'RUNNING', worker_id = $1, fence = fence + 1,
               lease_until = now() + interval '30 seconds'
WHERE run_id = (SELECT run_id FROM runs
                WHERE state = 'QUEUED' AND pool = $2
                ORDER BY priority, scheduled_for
                LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING run_id, fence, payload;

-- heartbeat and complete only count if the fence still matches
UPDATE runs SET lease_until = now() + interval '30 seconds' WHERE run_id = $1 AND fence = $2;
UPDATE runs SET state = 'SUCCEEDED' WHERE run_id = $1 AND fence = $2;   -- 0 rows: you lost the lease
  • Heartbeats: the worker extends its lease every third of the lease time (every 10 s for a 30 s lease). A long job keeps its lease as long as the worker is alive.
  • Reaper: a small loop finds RUNNING runs whose lease_until has passed and puts them back to QUEUED. Queues like SQS do the same thing with a visibility timeout.
  • Fencing: a worker can freeze (a long garbage collection pause, a network cut) and wake up still thinking it owns the run. The fence number stops its late writes, and the run id passed downstream stops repeated side effects.
  • Lease length is a trade-off: short leases bring crashed runs back quickly but need more heartbeats and expire by mistake during pauses. Long leases are calm but leave a crashed run invisible for minutes. Try it in the lab below.
  • Timeout is separate: timeout_s stops a run that heartbeats forever because it is stuck in a loop. The lease answers "is the worker alive?"; the timeout answers "is the job making progress?".

Try it: lease timeout vs duplicates

  • Lab

Runs take 20 seconds on average (some much longer, as real jobs do), and each worker has 4 slots. About 1 run in 500 is on a worker that crashes. Pick the load, the fleet size and the lease, and see what happens to start lag, duplicate runs and crashed runs.

Lease timeout

Rough model: run times are exponential with a 20 s mean. Without heartbeats, a run longer than the lease is handed to a second worker while the first is still going. With heartbeats, duplicates come only from workers that freeze for longer than two thirds of the lease (1% of runs pause, and pauses are rarely longer than a few seconds). Queue wait uses a standard many-server approximation. A crashed run waits for its lease to expire before anyone retries it.

At-least-once and idempotent jobs

  • Deep dive 4
  • Delivery guarantees
  • Idempotency keys

A scheduler can promise "at least once" or "at most once". It can't promise "exactly once" when the job talks to the outside world, because a worker can finish the work and die before it says so.

  • Choose at least once: a missed payroll run is far worse than a repeated one that does nothing. So every gap (crash, lost lease, scheduler failover) is closed by running again.
  • Make the repeat harmless: each run carries a stable key, run_id = job_id@scheduled_for, shared by all its attempts. The job passes it as the Idempotency-Key to anything it calls, or writes it next to its effect.
  • Common patterns: upsert by a natural key (the report for 18 Nov), a processed_runs table written in the same transaction as the effect, or a conditional write (set status to SENT only if it is PENDING).
  • For jobs that can't be made safe: offer overlap: skip (never two copies at once) and max_attempts: 1 (at most once). The owner then accepts that a crash means a missed run, and gets alerted instead.
  • Effectively once: at-least-once delivery plus idempotent effects gives the result people actually want: the work happens once, even if the code runs twice.

Interview line: "Exactly-once execution isn't possible with side effects. I give at-least-once with a stable run id, and the job uses that id to make repeats do nothing."

Retries and dead letters

  • Deep dive 5
  • Dead-letter queues
  • Retries in a pipeline
  • Sort failures first: timeouts, 5xx errors and 429s are worth retrying. A 400, a missing file or bad input will fail the same way every time, so stop at once and dead-letter it.
  • Back off with jitter: wait random(0, min(cap, base × 2attempt)). With a 10 s base and a 1 hour cap, five attempts are spread over roughly 5 minutes, and runs that failed together don't all retry in the same second.
  • Retries go through the wheel: a retry is the same run id with attempt + 1 and a new due time. It takes the same path as everything else, so there is no special retry machinery to break.
  • Dead letters: after max_attempts, store the run with its last error, payload and all attempts in a per-tenant dead-letter table, alert the owner, and give them a replay button once the bug is fixed.
  • Retry budgets: when a downstream service is down, retries can turn 1× load into 5×. Cap retries per target (say at 10% of normal traffic) and open a circuit breaker so the scheduler stops hammering it.
  • Overlap: a job every minute that takes 3 minutes piles up. Let the job choose: allow overlap, skip the new run while one is still going, or queue it.

Priorities and fairness

  • Deep dive 6
  • Rate limiting
  • Per-host queues in a crawler

At 02:00 the analytics team enqueues 1M backfill runs and the payments team enqueues 1,000 settlement runs. With one first-in, first-out queue, payments waits 10 minutes behind analytics. That is the bug fairness fixes.

  • Priority classes: high (paging, money), normal, low (reports, backfills). Separate queues, served by weight, for example 70 / 25 / 5. Weights rather than strict order means low still moves, and aging (a run's priority rises the longer it waits) means nothing waits forever.
  • A queue per tenant inside each class: the dispatcher takes turns between tenants (deficit round robin: each tenant gets a share of slots per round, weighted by plan). A tenant with 1M runs gets its share, not the whole fleet.
  • Quotas: a cap on concurrent runs per tenant, on registered jobs, and on "run now" calls a minute. Quotas protect the fleet; fair queuing protects the other tenants.
  • Pools: separate worker pools for different hardware (GPU, large memory) and for blast radius: critical tenants get a dedicated pool so a bad deploy on the shared one doesn't touch them.
  • The 02:00 example, fixed: with equal shares, payments' 1,000 runs get about half the slots right away and finish in seconds; analytics drains over the next ten minutes, which is fine for a backfill.

"Jobs live in a sharded database with a precomputed next_run_at. Jobs are hashed into partitions, and each partition has one scheduler, chosen through etcd leases. Once a minute each scheduler reads what is due in the next 60 seconds into a timing wheel with one-second slots. When a slot comes up it inserts runs keyed by job id plus scheduled time, so a double fire is harmless, and puts them on per-tenant, per-priority queues. A fair-share dispatcher leases runs to workers for 30 seconds; workers heartbeat, and a fence number rejects late results from a worker that lost its lease. Delivery is at least once, jobs use the run id as an idempotency key, failures retry with jittered backoff through the same wheel, and after five attempts they land in a dead-letter table the owner can replay."
