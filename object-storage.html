Object storage

A huge, cheap key-value store for files. You put whole objects in, you get whole objects out, and the store keeps them safe across many disks.

The object model

Object storage (Amazon S3, Google Cloud Storage, Azure Blob) holds photos, videos, backups, logs and build files. A database holds the facts about them; the bytes live here.

The model is small. A bucket is a named container. Inside it, each object has a key (its name), the bytes, and metadata.

PartWhat it isExample
BucketA container with its own access rules, region and settingsacme-user-uploads
KeyThe object's full name. The namespace is flat: / is just a character, and "folders" are shared prefixesu/42/avatars/9f3c.jpg
BytesThe content, from 0 bytes to terabytes, always read and written as a wholea 2.4 MB JPEG
System metadataSize, last modified, Content-Type, ETag (a hash of the content), storage classimage/jpeg
User metadataYour own small key-value pairs, sent as x-amz-meta-* headersx-amz-meta-owner: 42
Version IDWith versioning on, every overwrite keeps the old copy under a new version3HL4kqtJ...

The API is plain HTTP: PUT, GET (with an optional byte Range), HEAD, DELETE and LIST by prefix. There are no partial updates. To change one byte you write the whole object again.

Since December 2020, S3 gives strong read-after-write consistency: once a PUT returns, every GET and LIST sees the new object. S3 also supports conditional writes (If-None-Match: *), so two writers cannot both create the same key.

Throughput scales by key prefix. S3 serves at least 3,500 writes and 5,500 reads per second per prefix, and splits busy prefixes over time. Spread hot keys over many prefixes (for example a short hash at the start) if one prefix gets a sudden burst.

Presigned URLs

Do not send big files through your app servers. Let the client talk to the object store directly, with a short-lived, signed permission slip.

A presigned URL is a normal object URL plus query parameters: who signed it, when it expires, and a signature. The signature is an HMAC over the method, bucket, key, expiry and any signed headers, made with the server's secret key. The store recomputes it. If anything was changed, or the time has passed, the request fails with 403.

PUT https://acme-user-uploads.s3.amazonaws.com/u/42/9f3c.jpg
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Credential=AKIA.../20261118/us-east-1/s3/aws4_request
  &X-Amz-Date=20261118T101500Z
  &X-Amz-Expires=900
  &X-Amz-SignedHeaders=content-type;host
  &X-Amz-Signature=5d672d79c15b13162d9279b0855cfba6789a8edb4c82c400e06b5924a6f2b5d7
  • Scope it tightly. One method, one key the server picked (never the client's file name), a short expiry. 5 to 15 minutes is common. S3 allows at most 7 days.
  • Limit what can be sent. Sign Content-Type so the client cannot swap it. For browser forms, a presigned POST policy can also cap size (content-length-range).
  • Downloads too. A presigned GET serves private files without making the bucket public. Behind a CDN, use the CDN's own signed URLs or cookies instead, so the edge can cache.
  • Trust the event, not the client. The client saying "done" proves nothing. Mark the file ready when the store's "object created" event arrives and the worker has checked it.

Multipart and resumable uploads

One PUT to S3 can carry at most 5 GiB. Long single uploads are also fragile: a dropped connection at 95% means starting over. Multipart upload fixes both.

S3 limitValue
Single PUTup to 5 GiB
Part size5 MiB to 5 GiB (the last part can be smaller)
Parts per uploadup to 10,000

Pick a part size from the file size. A 100 GB file in 8 MiB parts needs 11,921 parts, which is over the limit. In 16 MiB parts it needs 5,961, which fits. Most SDKs use 8 to 64 MiB parts and upload 4 to 10 at once.

Resuming after a crash

The uploadId is the resume token. Save it (with the file's hash) on the device. After a restart, call ListParts to see which parts the store already has, upload only the missing ones, then complete. A phone that loses signal at 95% sends the last 5%, not the whole file.

Google Cloud Storage offers the same idea as a "resumable upload" session URL, and the open tus protocol does it over plain HTTP. File sync tools go one step further: they split files by content and skip blocks the server already has (see file sync).

Unfinished uploads are not free. Their parts are billed until you abort them. Add a lifecycle rule that aborts incomplete multipart uploads after a few days.

Replication vs erasure coding

Disks fail every day in a big fleet. The store must keep enough spare information to rebuild any lost piece before the next failure hits.

Replication (3×)Erasure coding (k+m)
Raw space per TB stored3 TB(k+m)/k TB, e.g. 1.5 TB for 6+3, 1.4 TB for 10+4
Losses survived2m
Repair one lost pieceRead 1 copyRead k pieces over the network
Small readsOne diskUsually one data piece; k pieces if a disk is down
CPUNoneEncode on write, decode on degraded reads
Good forHot, small, often-changed data; metadataLarge, cold or warm objects: the bulk of an object store

Durability is about two things: how much spare information you keep, and how fast you repair. Data is lost only when more pieces die than you can spare, all inside one repair window. So a faster repair is worth as much as an extra copy. Real stores also spread pieces across racks and zones, so one power cut cannot take several pieces at once.

Try it: cost vs durability

Pick a scheme, then change how often disks die, how long repair takes, and what raw disk costs. The table compares all schemes under the same settings.

Scheme
SchemeRaw / stored$ per TB-monthDurabilityRepair reads per PB-year

Illustrative model. A stripe (one object's pieces) loses data when one disk fails and m more of its disks fail before the first repair ends. Yearly loss ≈ n × AFR × C(n−1, m) × (AFR × repair hours / 8,760)m, where n is pieces per stripe. Durability nines = −log10(yearly loss). It assumes independent failures, so it overstates real durability; correlated failures (a rack, a zone, a bad firmware batch) dominate in practice. Repair reads assume each failed disk is full and is rebuilt by reading k pieces per lost piece (1 for copies).

Storage classes and lifecycle

Most stored data is rarely read after its first few weeks. Storage classes trade a lower monthly price for slower or costlier reads, plus a minimum time you pay for.

1 PB in Standard costs about $23,000 a month (using 1 PB = 1,000,000 GB). In Deep Archive it costs about $990. The catch is the read: a restore takes hours and costs per GB.

Lifecycle rules

Lifecycle rules move or delete objects by age, so nobody has to remember. A rule matches a prefix or tag, and the store runs it in the background.

rules:
  - prefix: "raw-uploads/"
    transition: { after_days: 30,  to: STANDARD_IA }
    transition: { after_days: 180, to: GLACIER_IR }
  - prefix: "tmp/"
    expire:     { after_days: 7 }
  - all objects:
    noncurrent_versions: { expire_after_days: 30 }
    abort_incomplete_multipart: { after_days: 3 }

Do the maths on small objects. Moving millions of tiny files costs a per-request fee each, and the 128 KB minimum can make IA cost more than Standard. Pack small files into bigger archives first.

MIME types

Every object carries a Content-Type, set when it is written. Browsers and CDNs use it to decide what to do with the bytes: show an image, play a video, or download a file.

ContentMIME type
JPEG, PNG, WebP imageimage/jpeg, image/png, image/webp
MP4 videovideo/mp4
HLS playlist and segmentapplication/vnd.apple.mpegurl, video/mp2t
PDFapplication/pdf
JSONapplication/json
Unknown bytes (the default)application/octet-stream
  • Do not trust the client. The file name and the browser's guess can both lie. Check the first bytes (the "magic number") in the worker: a real PNG starts with 89 50 4E 47.
  • Never serve user uploads as HTML from your main domain. A file uploaded as text/html could run script in your users' sessions. Serve uploads from a separate domain, send X-Content-Type-Options: nosniff, and add Content-Disposition: attachment for anything that should download.
  • Get it right at write time. A wrong type means video that will not play or images that download. Changing it later means a copy of the object onto itself.

How it goes wrong

A public bucket

The classic data leak. Keep "block public access" on, serve private files through presigned URLs or a CDN with signed access, and alert on any policy that allows everyone.

Leaked or long-lived presigned URLs

Anyone holding the URL can use it until it expires. Keep expiry short, scope it to one key and one method, and never log full presigned URLs.

Orphans in both directions

A file row with no object (the upload never finished), or an object with no row (the row insert failed). Write the row as "pending" first, flip it on the store's event, and sweep old pending rows and unknown keys on a schedule.

Lost overwrites

Two writers PUT the same key and the last one wins silently. Use keys nobody else will pick (a random ID or a content hash), conditional writes, or versioning.

Hot prefixes

A sudden burst on one prefix gets 503 Slow Down until the store splits it. Spread keys across prefixes and retry with backoff and jitter.

The egress bill

Storing is cheap; reading out to the internet is not. Serving popular files straight from the bucket can cost far more than storing them. Put a CDN in front.

Saying it in an interview

"File bytes go to object storage and the metadata goes to the database. For uploads the client asks our API for a presigned URL, scoped to one server-chosen key with a 15-minute expiry, and uploads straight to S3, so our servers never carry the bytes. Anything over about 100 MB uses multipart with 16 to 64 MiB parts, in parallel, and the client keeps the uploadId so it can resume. We insert the file row as pending, and the S3 event drives a worker that checks the type and size, makes thumbnails and marks it ready. Reads go through a CDN with signed URLs. Lifecycle rules move objects to Infrequent Access after 30 days and abort unfinished uploads after 3. Underneath, the store uses erasure coding for durability at about 1.4 to 1.5 times raw space instead of 3 times."
