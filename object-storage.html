Object storage

A huge, cheap, durable key-value store for files. You put whole objects under a key and get them back by key; the store spreads the bytes over thousands of disks so they survive almost anything.

The object model

Every large system keeps its big bytes (photos, videos, backups, logs, build artifacts) in object storage, and keeps only small rows about them in a database.

The model is deliberately simple:

  • Bucket: a named container with its own region, access rules and settings.
  • Key: any string up to 1,024 bytes, like users/42/avatar.jpg. The namespace is flat: the slashes look like folders, but there are no directories. A "folder" is just a shared key prefix, and listing one is a range scan over sorted keys.
  • Object: the bytes plus metadata (size, content type, a checksum called the ETag, custom headers). Objects are immutable: you cannot change byte 500 in place. You write a whole new version.
  • Versioning (optional): every overwrite or delete keeps the old version, so a bad deploy or a mistaken delete can be undone.

The API is a handful of HTTP verbs: PUT an object, GET it (or a byte range of it), HEAD for metadata, DELETE, and LIST by prefix. There are no joins, no queries and no partial updates. That is why it scales so far and costs so little.

Amazon S3 has had strong read-after-write consistency since December 2020: once a PUT returns, every GET and LIST sees the new object. Older articles that warn about eventual consistency on S3 are out of date. Other stores differ, so check before you rely on it.

How it works inside

An object store splits into two very different systems: a small, fast metadata index that maps a key to where its bytes live, and a huge, slow data tier of storage nodes full of hard disks.

The write path

  1. A stateless front end checks the caller's signature and permissions.
  2. It cuts the object into chunks, adds redundancy (copies or parity, see durability) and writes the chunks to storage nodes chosen so no two land on the same disk, machine or, for the default class, zone.
  3. Once enough chunks are safely on disk, it records the key, version and chunk locations in the metadata index, and only then answers 200 OK. The metadata write is the commit point: before it, the object does not exist to readers.

The read path

The front end looks up the key, fetches the chunks it needs in parallel, checks their checksums, reassembles the bytes and streams them out. A Range header lets a client fetch just part of an object, which is how video players seek and how download tools fetch in parallel.

Background work never stops

With millions of disks, several fail every day. Scrubbers re-read data to catch silent corruption, and repair jobs rebuild lost chunks onto healthy disks. A garbage collector removes chunks whose objects were deleted or overwritten. The hash checks and repair traffic are a large share of what the cluster does all day.

Throughput scales with key spread. S3 handles at least 3,500 writes and 5,500 reads per second per prefix and splits busy prefixes automatically, so spreading keys over many prefixes (for example photos/7f/…, photos/a3/…) raises the ceiling. See hot partitions for why one busy prefix hurts.

Presigned URLs

Never stream user uploads through your own servers. Give the client a short-lived URL that lets it talk to the bucket directly.

A presigned URL is a normal object URL with a signature in the query string. Your app server computes the signature with its own credentials, scoped to one operation (PUT this key, or GET that key) and an expiry time. The store checks the signature; it never needs to know who the end user is.

https://media.s3.amazonaws.com/uploads/42/7d1c.jpg
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Credential=…/20261118/us-east-1/s3/aws4_request
  &X-Amz-Date=20261118T104000Z
  &X-Amz-Expires=900          ← valid for 15 minutes
  &X-Amz-SignedHeaders=content-type;host
  &X-Amz-Signature=3f9a…

Why it matters: a 2 GB video passing through your API would tie up a server thread, its memory and its network for minutes. With a presigned URL, your API handles one tiny request to hand out the URL and the bytes go straight to the store, which is built for that load.

  • Keep expiry short: minutes, not days. Anyone holding the URL can use it until it expires. S3's maximum is 7 days, and a URL signed with temporary credentials dies when they do.
  • Pick the key on the server, never from the client's file name: uploads/{user_id}/{random_id}. This stops overwrites of other people's files and path tricks.
  • Limit what can be sent. A presigned PUT can bind the Content-Type header. A presigned POST with a policy can also cap size (content-length-range) and require a key prefix.
  • Confirm after upload. Have the client call your API when it is done, or listen for the store's "object created" event, then check size and type before marking the file usable.
  • Downloads too: for private files, hand out a presigned GET for a few minutes after checking permissions, or use signed CDN URLs so the edge can cache them.

Multipart and resumable uploads

One long PUT of a big file is fragile: if the connection drops at 90%, you start again. Multipart upload splits the file into parts that upload independently, in parallel, and can be retried one at a time.

The limits (Amazon S3)

LimitValue
Largest single PUT5 GB
Parts per upload1 to 10,000
Part size5 MiB to 5 GiB (the last part can be smaller)
Largest object50 TB (raised from 5 TB in December 2025)

Because of the 10,000-part cap, pick the part size from the file size:

part size ≥ file size ÷ 10,000  ·  50 GB → at least 5 MB  ·  1 TB → at least 100 MB

In practice 8 to 64 MB parts work well for most files: small enough that a retry is cheap, large enough that per-request overhead stays small. Use multipart for anything over about 100 MB.

Resuming

If the client crashes, it keeps the uploadId, asks the store which parts it already has (ListParts) and uploads only the rest. For browsers and phones, the open tus protocol wraps the same idea in a standard resumable-upload API. The file sync design goes one step further and names each block by its hash, so unchanged blocks are never uploaded at all.

Parts of an upload that is never completed or aborted are stored and billed, but invisible in normal listings. Always add a lifecycle rule that aborts incomplete multipart uploads after a few days.

One surprise: the ETag of a multipart object is not the MD5 of the file. It is a hash of the part hashes with -N on the end (N = number of parts), so do not compare it with a local MD5. Send a per-part checksum (CRC32C or SHA-256) instead and let the store verify it.

Try it: replication vs erasure coding

Store a data set with plain copies or with erasure codes. Compare how much disk you pay for, how many failures you can survive, the modelled durability, and how much data has to move across the network when one 20 TB disk dies.

Scheme

Illustrative. Assumes $10 per raw TB per month for disks, servers and power, 20 TB disks, and independent failures. Durability uses the usual quick estimate: the chance that, after one chunk is lost, enough others in the same stripe fail before repair finishes. Real systems lose data mostly through correlated failures (a rack, a bad firmware batch, a software bug), so providers quote about 11 nines, not the 15 this model can show.

Durability: copies or codes

Replication

Write each chunk to three disks in three failure domains. Simple, fast to read (any one copy will do) and fast to repair (copy one chunk from a survivor). But you pay for 3× the disk, and at petabyte scale disk is the bill.

Erasure coding

Reed-Solomon RS(k, m) cuts data into k chunks and computes m parity chunks, so that any k of the k + m chunks can rebuild the original. RS(6, 3) stores 9 chunks for 6 chunks of data: 1.5× overhead, and it survives any 3 losses, one more than three copies survives.

3 copiesRS(6, 3)RS(10, 4)

The trade: erasure coding halves the disk bill but makes every repair read k times more data over the network, and makes small objects awkward (a 4 KB object split six ways is all overhead). Real systems mix both: new or small objects start replicated, then a background job re-encodes them once they are cold. Microsoft Azure uses local reconstruction codes, which add small local parity groups so most repairs read a few chunks instead of all k.

Across regions, the same choice repeats: a full copy in a second region (2× again, simple) or a code spread across three or more regions (cheaper, but every read during an outage crosses regions).

Storage classes and lifecycle

Most data is read a lot in its first weeks, then almost never. Storage classes let you pay less per GB in exchange for slower or pricier reads.

Lifecycle rules move or delete objects automatically by age and prefix, so nobody has to remember:

uploads/tmp/      expire after 1 day
logs/             Standard → Standard-IA at 30 days → Glacier Flexible at 90 → delete at 400
backups/          Glacier Deep Archive at 7 days
*                 delete noncurrent versions after 30 days
*                 abort incomplete multipart uploads after 7 days

Watch the small print: moving millions of tiny objects costs a fee per object, and deleting before the minimum duration still bills the full minimum. Cold classes save money on data you are sure you will not read.

Content types

The store does not care what the bytes are, but browsers do. Each object carries a Content-Type (a MIME type such as image/jpeg, video/mp4 or application/pdf) that is returned as a header on every GET. If nobody sets it, it falls back to a generic binary type, and the browser downloads the file instead of showing it.

  • Set it at upload, and bind it in the presigned URL so the client cannot swap it.
  • Do not trust it. The client chooses the header and the file name. After upload, check the real type from the file's first bytes (magic numbers: JPEG starts FF D8 FF, PDF starts %PDF) before you process or serve it.
  • Serve user uploads from a separate domain (like usercontent.example.com), with X-Content-Type-Options: nosniff, and Content-Disposition: attachment for anything that is not a known-safe image or video. Otherwise an "image" that is really HTML can run script on your main site.
  • Set Cache-Control too, so the CDN in front of the bucket knows how long to keep each object. Content-hashed keys like app.3f9a1c.js can be cached for a year.

How it goes wrong

Public buckets

The most common real incident is not lost data but leaked data: a bucket left readable by anyone. Block public access at the account level, serve public files through a CDN with origin access control, and hand out presigned URLs for everything else.

Accidental deletes and ransomware

Durability protects against disks failing, not against your own delete calls. Turn on versioning for important buckets, use object lock (write once, read many) for backups, and copy critical data to a second account.

Hot prefixes and request limits

A burst of writes under one prefix gets 503 Slow Down until the store splits it. Spread keys with a hash prefix, and retry with exponential backoff and jitter.

Lots of tiny objects

Every object costs a metadata entry and a request fee, and IA classes bill at least 128 KB each. A billion 1 KB log lines as separate objects is slow to list and expensive. Batch small records into larger files (Parquet, or compressed log segments) before storing them.

Listing as a database

LIST returns 1,000 keys per page in key order and is slow over millions of keys. Keep an index of your objects in a real database, or use the store's inventory reports, instead of listing to find things.

Egress bills

Storing is cheap; sending bytes out to the internet is not (roughly $0.05–0.09 per GB from the big clouds). Put a CDN in front of anything popular, and keep compute that reads a lot of data in the same region as the bucket.

Saying it in an interview

"Media goes to object storage, and the database only keeps a row with the object key, size, type and owner. Uploads skip our API: the client asks for an upload, we pick the key, start a multipart upload and return presigned part URLs that expire in 15 minutes. The client sends 16 MB parts in parallel, retries failed parts, and resumes with the upload ID if it crashes. When the store fires its object-created event, a worker checks the real file type, scans it and marks the row ready. Reads go through a CDN with signed URLs for private files. The store keeps data with erasure coding across three zones, about 1.5× raw disk for 11 nines. Lifecycle rules move objects to infrequent access after 30 days, to archive after 90, and clean up abandoned uploads."
