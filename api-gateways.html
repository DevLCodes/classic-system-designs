API gateways and service mesh

The front door and the hallways. A gateway is the one place every outside request enters, where you check who it is, how much it may do, and where it goes. A service mesh does the same jobs for the calls services make to each other, without changing their code.

Proxy, load balancer or gateway?

All three sit between clients and servers and forward requests. They differ in how much they understand about each request.

ComponentKnows aboutTypical jobs
Reverse proxyHTTP requests and responsesTLS termination, compression, caching, hiding the servers behind one address
Load balancerA pool of identical servers and their healthSpread requests, remove unhealthy servers (L4 or L7)
API gatewayYour API: routes, users, API keys, plansAuthentication, rate limits per client, routing to many different services, request shaping, API analytics

In practice one product often does all three. Nginx or Envoy can be a proxy, a load balancer and a gateway at once. The useful distinction is the job: a gateway applies API policy, the same rules for every service behind it, in one place.

What a gateway does

  • Authentication: verify a JWT's signature and expiry, or look up an API key, once at the edge. Services behind it receive a trusted user ID in a header instead of each re-implementing login.
  • Rate limits and quotas: per API key, per user, per plan ("free: 100 requests a minute"). See Rate limiting.
  • Routing: by path (/orders → orders service), by version (/v2), by header (send 5% of traffic to a canary).
  • Request shaping: size limits, schema validation, header clean-up, translating REST to gRPC.
  • Observability: one access log for every API call, request counts and latency per route and client, and a trace ID that follows the request through every service.

Keep business logic out of the gateway. It is shared by every team, so every change to it is risky and slow. If a rule is specific to one service, it belongs in that service.

Aggregation and backends for frontends

A phone's home screen might need the user, their recent orders and some recommendations. Making three round trips over a mobile network is slow. Two patterns help:

  • Aggregation: the gateway (or a GraphQL layer) calls the three services in parallel inside the data center, where a round trip is half a millisecond, and returns one combined response.
  • Backend for frontend (BFF): a small service per client type, owned by that client's team: one for web, one for iOS and Android, one for partners. Each shapes responses for its screens, and none of them has to compromise for the others.

The cost is one more hop and one more service to run, and the risk that a BFF slowly fills up with business logic that belongs in the core services.

Service mesh

With 200 services calling each other, every team needs timeouts, retries, mutual TLS, metrics and tracing on every call. A service mesh moves all of that out of application code into a proxy that runs beside each service instance (a sidecar, often Envoy). The application talks to localhost; the sidecar finds a healthy instance of the target, encrypts the connection, retries if allowed, and reports metrics.

Mesh gives youWithout a mesh
Mutual TLS between every pair of services, with certificates rotated automaticallyEach team manages certificates, or traffic inside the cluster is plain text
Uniform retries, timeouts and circuit breaking from configA different client library and different defaults in every language
Golden metrics (requests, errors, latency) for every callInstrumentation where someone remembered to add it
Traffic shifting for canaries and blue-green deploysCustom deploy scripts per service

The price: an extra proxy hop on every call (about a millisecond), more memory per pod, and a complex control plane to operate. Newer designs drop the per-pod sidecar for a shared per-node proxy (Istio's ambient mode) or kernel-level networking (Cilium with eBPF). With a handful of services, a good HTTP client library is enough.

Timeouts, retries and circuit breakers

Gateways and meshes are where resilience policy lives. Getting it wrong turns a small slowdown into an outage.

  • Timeouts on every call. Without one, a slow dependency holds threads and connections until the caller runs out and fails too. Set each timeout from the dependency's p99.9 latency, and make the caller's timeout longer than the sum of what it waits on.
  • Retries only for safe requests. Retry reads, and writes protected by an idempotency key. Never retry a timeout on a non-idempotent write blindly.
  • Exponential backoff with jitter. Wait 100 ms, 200 ms, 400 ms, each with a random spread, so thousands of clients don't retry in the same instant.
  • Retry budgets. Allow retries up to, say, 10% of normal traffic. When most calls are failing, retrying them only adds load.
  • Retry at one layer. If the app, its sidecar and the gateway each retry 3 times, one failing call becomes 4 × 4 × 4 = 64 attempts.
  • Circuit breakers. After too many failures, stop calling the dependency for a few seconds and fail fast (or serve a fallback). Then let a few test requests through; close the breaker when they succeed.
  • Bulkheads. Give each dependency its own connection pool, so one slow service can't use up every connection the caller has.

Try it: a retry storm

A service normally gets 10,000 requests a second and can handle 12,000. A bad deploy makes some of its calls fail. Choose how many times callers retry and what protects the service, and watch whether it recovers or melts.

Protection

Rough model: every failed attempt is retried up to the limit; load above 12,000 a second makes the excess fail too (overload feeds back into the failure rate); a circuit breaker opens when more than 30% of calls fail and serves a fallback while sending 5% of traffic as probes.

How gateways fail

The gateway is a single point of failure

Every request goes through it, so run it as a stateless fleet across zones behind an L4 load balancer, keep its config in version control, and roll config changes out gradually like code. Many large outages have been one bad gateway or proxy config pushed everywhere at once.

Rate-limit or auth store goes down

If the gateway checks a central Redis for every request and Redis is slow, everything is slow. Cache keys and token-validation keys locally, and decide in advance whether to fail open (allow) or closed (deny) for each check.

Retry storms

Retries multiply load exactly when a service is weakest. The lab shows how 20% failures plus 3 retries can push a service over its limit, where overload creates more failures and more retries. Budgets and breakers stop the spiral.

Head-of-line blocking from one slow route

A slow upstream can use up the gateway's worker threads or connections for every route. Per-route connection limits and timeouts keep one bad service from taking down the whole API.

Saying it in an interview

"Clients hit a stateless gateway fleet behind an L4 load balancer. The gateway terminates TLS, validates the JWT, applies per-client rate limits, and routes by path to the services, adding a trace ID. Mobile gets its own backend-for-frontend that aggregates calls. Inside, a service mesh gives us mutual TLS and uniform timeouts. Retries happen at one layer only, with exponential backoff, jitter and a 10% retry budget, and circuit breakers fail fast with a fallback, so a sick dependency can't drag down its callers."
