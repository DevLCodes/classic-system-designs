CDNs, PoPs and IXPs

A content delivery network keeps copies of your content in hundreds of small data centers close to users. Requests travel a few kilometers instead of across an ocean, and your own servers only see the small share the edge can't answer.

What a CDN does

Light in fiber covers about 200 km per millisecond. A user in Chennai fetching from a server in Virginia waits about 230 ms per round trip before any work happens, and opening a secure connection takes two or three round trips.

A CDN puts servers in hundreds of cities. The user's connection ends at the nearest one, 5 to 20 ms away. If that server has the file cached, it answers immediately. If not, it fetches the file from your server (the origin) over a connection it keeps open and warm, then caches it for the next user. Images, video, scripts, stylesheets and downloads are the obvious content to cache, but API responses that are the same for many users can be cached for a few seconds too.

PoPs and anycast

A point of presence (PoP) is a small CDN site in a city: a few racks of cache servers and routers, usually inside a shared data center. Large CDNs have hundreds of them.

Users get to the nearest PoP in one of two ways:

  • DNS steering: your cdn.shop.com is a CNAME to the CDN, whose DNS answers with the IP of a PoP near the user's resolver.
  • Anycast: every PoP announces the same IP address to the internet, and BGP routing carries each user's packets to the closest one in network terms. If a PoP goes down, it stops announcing and traffic flows to the next nearest within seconds. Anycast also spreads a DDoS attack across every PoP instead of letting it land on one.

IXPs and peering

The internet is thousands of separate networks (ISPs, mobile carriers, clouds, CDNs) connected to each other. An internet exchange point (IXP) is a building where many networks plug into a shared switch and exchange traffic directly, usually for free (peering), instead of paying a transit provider to carry it.

CDNs put PoPs at major IXPs (for example in Mumbai, Chennai, Frankfurt, Amsterdam, Singapore) and peer with as many local ISPs as possible. That gives them a short, cheap path straight into each ISP's network. Some go further and place cache servers inside ISPs' own networks (Netflix Open Connect, Google Global Cache), so popular video never leaves the user's ISP at all.

Why it matters in a design: the CDN's real value is its peering. Video at 26–50 Tb/s (see Video streaming) is only affordable because almost all of it is served from caches inside or next to the user's ISP.

Cache hierarchy and origin shield

With 300 PoPs, a new file can cause 300 misses, each one a request to your origin. A shield (or mid-tier) cache sits between the PoPs and the origin: PoPs ask the shield, and only the shield asks the origin. One request per file per shield instead of one per PoP.

The shield also collapses requests: if 5,000 users ask for the same new file in the same second, the CDN sends one request upstream and makes the rest wait for it. This is the same idea as stampede protection in Caching.

Cache keys, TTLs and purges

  • Cache key: by default the URL. Leave out query parameters that don't change the response (tracking tags like utm_source), or every variation becomes a separate cache entry and the hit ratio collapses. Use Vary only for headers that really change the response.
  • TTL: Cache-Control: public, max-age=31536000, immutable for files whose names include a content hash (app.3f9a1c.js): they never change, so cache them for a year. Short TTLs (seconds to minutes) for HTML and API responses.
  • Purge: to change cached content before its TTL ends, call the CDN's purge API by URL or by tag. Good CDNs purge worldwide in a second or two. Versioned file names are still better: deploy app.7b2e4d.js and nothing needs purging.
  • Stale content: stale-while-revalidate lets the edge serve the old copy while it fetches a new one, and stale-if-error keeps serving it if the origin is down.
  • Private content: never cache responses with personal data under a shared key. Use Cache-Control: private, or signed URLs and cookies for paid content.

Try it: what the edge saves

A user in Chennai loads files from an origin in the US, about 230 ms away. Choose the setup and the cache hit ratio, and see the latency the user feels and the traffic left for your servers.

Setup

Rough model: a new HTTPS connection costs 3 round trips (TCP, TLS 1.3, request); the PoP is 8 ms away and keeps a warm connection to the origin (one 230 ms round trip per miss); files average 200 KB; a shield turns misses from 50 PoPs into about a fifth as many origin requests.

More than caching

  • TLS at the edge: the expensive handshake happens 8 ms from the user, not 230 ms. This speeds up even uncacheable API calls.
  • Security: DDoS absorption, a web application firewall, bot detection and rate limits run before traffic reaches you.
  • Edge compute: small functions at the PoP (Cloudflare Workers, CloudFront Functions, Fastly Compute) for redirects, A/B test assignment, header rewrites, auth checks or personalizing a cached page.
  • Image and video work: resize and convert images to WebP or AVIF per device, and package video segments on the fly.

How CDNs fail

A low hit ratio

Random query strings, cookies in the cache key, or Vary: User-Agent split one file into thousands of entries. Watch the hit ratio per path and fix the cache key before buying more origin servers.

Caching something private

A response with one user's account page cached under a shared key gets served to everyone. Mark personal responses private and test with two accounts.

Purge storms and cold caches

Purging everything at once sends the full load to the origin, which was sized for 10% of it. Purge by tag, warm caches for big launches, and keep the shield on.

The CDN itself goes down

Global outages at single CDN providers have taken large parts of the web offline for an hour. For critical sites, keep a second CDN behind DNS and test switching to it.

Saying it in an interview

"Static files and media go through a CDN: anycast to the nearest PoP, content-hashed file names cached for a year, HTML for a minute with stale-while-revalidate. An origin shield collapses misses so the origin sees a few percent of requests. TLS terminates at the edge, which also helps uncacheable API calls, and the WAF and DDoS protection run there too. I'd track the hit ratio per path and alert if it drops, because a bad cache key can send 10× the load to the origin."
